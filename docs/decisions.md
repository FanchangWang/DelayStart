# DelayStart — 决策记录（D1–D118）

> 这份文档只回答一个问题：**当前方案为什么长这样**。
>
> 每条给出「结论」与背后的取舍；被后续决策推翻的，不再单独占位，直接并入取代它的条目（**编号仍然有效**，代码注释、提交信息、测试用例都按编号引用）。
> 当前实现以 [`design.md`](design.md) 为准，技术陷阱见 [`pitfalls.md`](pitfalls.md)。想找某个编号：直接搜索 `D编号`。

**分组**：一、调度端：进程与启动链路 · 二、调度端：交互与收尾 · 三、扫描与接管 · 四、UWP 支持 · 五、管理端界面 · 六、安装分发与真机验收 · 七、工程约定与基础设施 · 八、自启动项守卫

## 一、调度端：进程与启动链路

### D1 调度端要不要做成独立进程

**结论**：独立轻量进程，不寄宿在管理端里。
**背景**：登录时不该为了等几个延时把整个 WinUI 3 框架拉起来。
**为什么不是别的**：让管理端常驻 = 每次登录都背一个 UI 进程；做成 Windows 服务 = 会话 0 隔离，启动出来的程序用户看不见也交互不了。
**后续**：本条只定了"独立进程"，UI 形态在 D24 重新评估。

### D13 几十分钟的长延时怎么调度

**结论**：统一由调度端驻留等待，不拆成多个计划任务。
**背景**：曾考虑"每条目一条延迟计划任务"，但那样「跳过剩余」「立即启动剩余」这类运行中操作全部无法实现。
**代价**：调度端要驻留到最后一个条目启动为止（短任务场景下就是 10–60 秒）。

### D14 调度端有没有主窗口

**结论**：无主窗口，只有托盘图标 + 点击弹出面板。
**背景**：它是基础设施进程，登录瞬间弹窗会打断用户。
**后续**：面板行为在 D71–D73 演进为"完成弹面板、倒计时关闭即退出"。

### D24 调度端用什么 UI 技术（重开 D1）

**结论**：**纯 Win32 + NativeAOT**，托盘与面板全走 P/Invoke。
**背景**：调度端在登录瞬间被拉起，冷启动 < 0.3s、体积 ≤ 6MB 是硬指标（NFR-1）。
**为什么不是别的**：WinForms / WPF + `PublishAot` 被 SDK 直接拦（NETSDK1175），放行只能押注内部属性；WinUI 3 没有托盘 API，且冷启动超指标。
**代价与约束**：托盘、面板、主题、字体全部自绘；禁 `.resx`、反射绑定、动态 COM（约束条款持续生效，见 R11）。

### D27 Phase 1 要不要写 P/Invoke

**结论**：Phase 1 只做接口与纯逻辑，P/Invoke 推到 Phase 4。
**背景**：P/Invoke 的正确性只能在真实交互会话里验证（UIPI、提权、令牌），构建环境里写完也测不出来。
**后续**：Phase 4 集中落地 Win32 层；D69 就是那阶段真机暴露的缺陷。

### D38 普通程序怎么降权启动（第一次尝试）

**结论**：双进程代理 —— 调度端（High）拉起一个 Medium 代理，代理再启动目标。
**背景**：接管来的条目大多是普通用户程序，而调度端自己是管理员身份，直启会得到 High 进程（部分程序因此行为异常）。
**后续**：⚠️ 已被 D40 整体取代。

### D39 D38 的修订（单任务 + 令牌握手）

**结论**：把双进程代理收敛为"单任务 + 令牌握手"。
**后续**：⚠️ 随 D38 一起作废。

### D40 降权机制再评估（七方案对照）

**结论**：**调度端亲自降权** —— `GetShellWindow` 取外壳令牌 → `DuplicateTokenEx` → `CreateProcessWithTokenW`；`.lnk` / UWP 交给 explorer 外壳委托；删除代理进程。
**背景**：D38/D39 的双进程代理在现场连续出问题，于是把当时能想到的七条降权路径全部实测对照。
**实测否掉的**：直接把 explorer 进程令牌交给自己 → 必报 `Win32Error=5`；`CreateProcessAsUserW` → 1314（缺权限）；网上流传的 COM `Shell.Application.ShellExecute` "降权技巧" → 实测根本不降权，**禁用**。
**红线**：降权链任何一步失败 = 该条目判失败并继续，**绝不提权回退**（否则用户设的"普通权限"会被静默改成管理员）。
**后续**：D70 为其补上 uiAccess 目标的例外路径。

### D70 uiAccess 目标（如 Quicker）启动报 740

**结论**：预检目标清单，命中 `uiAccess="true"` 就走**降权中转器链**：调度端 A（High）写作业 JSON → 降权拉起 `DelayStart.LaunchBroker.exe` B（Medium，AOT 单文件）→ B 对目标 C 调 `ShellExecuteEx`（由 AppInfo 服务赋 UIAccess 并按调用方身份抬 IL）→ B 把 **C 的**真实状态（PID / 秒退 / Win32 错误）经结果 JSON 回写，调度端轮询读取。
**背景**：用户报告 Quicker 启动失败报 740。排查结论是 **uiAccess 目标不存在任何降到 Medium 的路径**：`SetTokenInformation(TokenUIAccess)` 需要 `SeTcbPrivilege`（只有 SYSTEM 有），而 `CreateProcessWithTokenW/AsUser` 不会自动把清单声明应用到复制出来的令牌 —— 缺任一前提一律报 `ERROR_ELEVATION_REQUIRED(740)`，且不告诉你缺哪个。⇒ 这该特判为"目标是 UIAccess 程序"，而不是当管道 bug 修。
**一个反直觉的实测结论**：走 explorer 委托"成功"也不是 Medium —— shell 经 AppInfo 服务（`RAiLaunchAdminProcess`）对合规 uiAccess 目标**静默把完整性级别提到 High**（受限管理员 → 0x3000，无 UAC 弹窗）。"Medium + UIAccess"这个组合在 Windows 里不存在。
**配套修复**：
- `SHELLEXECUTEINFOW` 必须补 `dwHotKey` 之后的 `union { hIcon; hMonitor; }` —— x64 下 `sizeof` 必须是 **112**；漏掉是 104，`cbSize` 传错 + 原生越过缓冲写 `hProcess`（堆越界）。调用前做 ABI 自检，非 112 拒绝调用。
- Broker 调 `ShellExecuteEx` 前必须 `CoInitializeEx(NULL, COINIT_APARTMENTTHREADED | COINIT_DISABLE_OLE1DDE)` —— shell 函数要求 STA 线程，未初始化 / MTA 时报 `ERROR_ACCESS_DENIED(5)`。
- 作业 / 结果契约 = `BrokerLaunchJob` / `BrokerLaunchResult`（Core，`BrokerJsonContext` 源生成）；B 自身退出码只表达"回写是否成功"。
**权限链**：A(High) → B(Medium) → C（由 AppInfo 决定，受限管理员下等同手动双击）。

## 二、调度端：交互与收尾

### D15 完成通知策略

**结论**：默认"仅失败时通知"，三档可配（仅失败 / 总是 / 从不）。
**背景**：调度大多数时候是顺利的，成功通知等于噪音。
**后续**：载体在 D71 从气泡改为面板，但"要不要**主动**弹"的语义不变。

### D16 面板上要不要放「退出调度」

**结论**：第一版不做。
**背景**：调度端一退出，剩余条目就永远不会启动，而用户看不出这个后果。
**后续**：D71 起完成态有「退出」（此时已无剩余条目，退出是安全的）；启动中仍然没有裸退出，只有「跳过剩余任务并退出」这条显式路径。

### D17 启动失败的长期策略

**结论**：**不自动处理** —— 保持接管状态 + 提醒逐级升级（第 1/2 次可忽略；≥3 次角标常驻、告警条不提供忽略），唯一出口是用户点「移出延时启动」。
**背景**：备选是"多次失败后自动恢复自启动"，但那等于软件替用户改了系统状态，违反"不替用户做决定"。
**影响**：`FR-6.8`–`FR-6.10`；连续失败次数**不落盘**，由 `FailureStreakService` 扫 `runs/` 现算。

### D18 点击完成通知做什么

**结论**：打开管理端运行日志并定位到本次运行（`--goto-log --run=<id>`）。
**背景**：看到"有失败"之后，用户的第一诉求是"哪个失败了、为什么"。

### D19 运行中的调度状态怎么共享给管理端

**结论**：调度端每次状态变化原子重写 `state/current-run.json`（含 pid），管理端用 `Process.GetProcessById` 探测判"进行中"，不引入 IPC。
**背景**：两个进程全程提权，跨进程通信的备选（命名管道 / 共享内存）都要额外的协议与版本管理。
**已知取舍**：该文件是易失的，读不到就当"没有调度在跑"。这是**刻意设计**（实时状态下次调度会整体重写，不值得为它引入三态接口），不是缺陷。

### D37 时间轴视图

**结论**：需求页与模拟调度**两处都砍**，模拟调度改"进度视图"。
**背景**：延时值普遍很短（0–60s），把时间轴画出来的信息量低于实现与维护成本。

### D71 调度端 UI v2（面板 + 菜单）

**结论**：完成通知从气泡改为**自动弹出面板**（已开则激活）；启动中面板不自动关闭（删除 `WM_ACTIVATE` 失焦即关）；完成后倒计时自动关闭（成功 10s / 失败 60s，鼠标移入暂停且移出**不重置**）；**完成态关闭面板 = 退出调度器进程**，托盘图标随之移除（启动中 ✕ 只 `SW_HIDE`）；右键菜单两套（启动中 / 启动完毕，完成态含「退出」）；管理端通知策略文案改为「弹出面板」。
**背景**：三条限制叠加导致气泡不能承担完成通知 —— elevated 进程发不了 `AppNotification`；AOT 用不了 WinRT 通知 API；Win11 气泡不进通知中心且时长由系统控制。
**设计意图**：面板可停留、可看失败明细、可跳日志；气泡只能显示一行且会自己消失。

### D72 同一个收尾动作在菜单与面板上语义不同

**结论**：拆成两套入口。
- 菜单「立即启动剩余任务」→ 遵循通知策略（该弹就弹、该退就退）；
- 菜单「跳过剩余任务并退出」→ 不弹面板、**不等** 1.5 秒复查窗口，`Launching` 条目一并标 `Skipped`，落盘归档后立刻退（**菜单文案保持原样**）；
- 面板上的两个按钮 → **必定**留在面板上给结果（切完成态 + 起倒计时，不退出），面板按钮文案去掉"并退出"。
**背景**：用户已经手动打开面板在看，点了按钮之后面板反而消失是明显倒退；而菜单那条语义就是"不看结果直接走"。
**实现要点**：引擎用 `_panelRequestedCompletion` 标记"面板发起 → 必弹"；菜单跳过走 `Finish(quitImmediately: true)` 直接进退出分支，**不经过面板决策**，因此不需要单独的抑制标记。
**代价**：菜单跳过时 `Launching` 条目拿不到真实成败判定（用户明确不想等）。

### D73 已显示的面板被通知策略关掉

**结论**：判据补上"面板此刻已显示"这一条 —— **`NotifyMode` 只管"要不要主动弹"，管不到已经弹出的面板**。
**背景**：`FailuresOnly` + 全部成功 + 用户手动打开着面板 → 判定不弹 → 进程退出 → 面板连同托盘毫无理由地消失。
**后续**：这次修复连带把收尾判据抽成 `CompletionPolicy` —— 三个连续缺陷（D71/D72/D73）都出在这一处，而调度端是 NativeAOT WinExe、无法单测。

## 三、扫描与接管

### D2 `.lnk` 与 UWP 条目的目标是什么

**结论**：解析出真实目标并保存；但**启动**时 `.lnk` / UWP 仍走外壳委托（不自己实现外壳语义）。
**后续**：D40 明确委托路径同样要降权。

### D3 总览页的「开机调度任务」开关

**结论**：原设计是「开 = 注册任务 / 关 = 删除任务」，**D68 废止**：开关删除，改为状态卡 + 每次启动自检自愈。
**背景**：开关让"删除任务"变成用户可点的动作，而删掉之后没有任何东西会提醒他"你的延时启动已经失效了"。

### D5 「系统启动项」页的范围

**结论**：只做服务的一键 `delayed-auto` 切换；驱动 / Winlogon / 登录脚本纯只读。
**背景**：驱动和 Winlogon 改坏会导致无法登录，收益远小于风险。

### D9 `.lnk` 目标与图标解析

**结论**：做 —— `IShellLinkW` + `IPersistFile` 解析目标/参数，`IShellItemImageFactory` 取图标。
**代价**：两者都在 COM 之上，因此只能待在 `DelayStart.Management`（Core 必须 AOT 兼容）。

### D66 过滤"名字带 Microsoft"的任务时误伤

**结论**：受保护文件夹判据必须写 `@"\Microsoft\"`（**带尾分隔符**），并钉死为只认**根级** `\Microsoft\` 文件夹。
**背景**：原判据 `@"\Microsoft"` 少一个尾分隔符，把名字里含 "Microsoft" 的第三方任务（如 Edge 更新）整批静默滤掉 —— 用户看到的现象只是"这些项不显示"，没有任何报错。
**配套**：16 例单测 + 红/绿对照钉住。

### D67 禁用一条任务时连带关掉它的其他触发器

**结论**：禁用粒度分四层 —— 任务级已关 → 一个字节不动；触发器 ≤1 → 切任务级；>1 → **全部**切登录/启动触发器；启用时先开任务级再开触发器。
**背景**：`task.Enabled=false` 是任务级开关，会连带关掉同一任务的所有触发器；而"只切第一个触发器"会导致程序照常自启 + 我们再拉一次 = **启动两次**。
**实测否掉的**：用 `Trigger.Id` 记账 —— 实测 id 普遍是空串，不能当标识。
**细节**：改动无变化时不调 `RegisterChanges()`（会刷新时间戳、触发 `RegistrationTrigger`）。

## 四、UWP 支持

### D4 UWP 能不能延时启动

**结论**：做，但 UI 文案必须写明"延时启动 UWP = 禁用系统自启 + 到点激活，会绕过系统启动管理"。
**背景**：UWP 自启动由系统 AppModel 调度，第三方**无法延后**它；能操作的只有 `State=0/2` 两个状态。

### D28 UWP 用什么方式激活

**结论**：`explorer.exe shell:AppsFolder\<AUMID>`，零 COM。
**背景**：AOT 没有 built-in COM —— `Marshal.GetObjectForIUnknown` / `[ComImport]` 激活在 AOT 产物里运行时必抛 `PlatformNotSupportedException`。
**判定**：UWP 没有 PID，收到 `null` 快照直接判成功。

### D41 UWP 启动失败的修复

**结论**：以**解析名**（`shell:AppsFolder\…`）为主判据；新增 `UwpAppIdResolver` 把 TaskId 映射到真实 AppId；委托路径也要降权。
**背景**：注册表子键名是 `StartupTask.TaskId`，而正确的 AUMID 需要读 `AppxManifest.xml` 才能拿到 —— 两者不是一回事。

### D43 总览结果列空白 + 管理员身份下 UWP 启动失败

**结论**：结果列空白 = 拆两份互斥 `TextBlock`（`Foreground` 绑 null 会切断依赖属性继承链）；UWP 判定提前。
**后续**：⚠️ 其中"管理员身份导致失败"的定性后来被 D44 / D45 连续更正。

### D44 UWP 管理员身份（推翻 D43 的定性）

**结论**：真因不是权限，而是**裸 AUMID 不是文件路径**（会被 `File.Exists` 判"目标不存在"）。
**后续**：⚠️ 机制假设又被 D45 推翻。

### D45 UWP 启动身份（二度更正）

**结论**：**UWP 进程恒为普通用户身份**，中转外壳用谁的令牌都不改变结果 ⇒ 编辑器不提供管理员胶囊。
**方法论教训**：涉及令牌 / 权限 / 完整性的结论，**必须测到进程完整性级别**才能收口，不能停在"启动成功"（D43→D44→D45 两度翻转就是没测到底）。

### D46 手动添加 UWP 入口

**结论**：入口 + `GetAppListEntriesAsync()` 应用列表 + 复用 `IconProvider` + 参数框置灰；配置里存**解析名**而非裸 AUMID。
**背景**：`GetAppListEntriesAsync()` 是唯一能同时拿到显示名与真实 AUMID 的通道。

### D54 UWP 只读条目的字段

**结论**：只显示 UWP 应用信息，名称 / 命令行 / 工作目录全部隐藏。
**背景**：UWP 没有传统意义上的"路径 / 工作目录"，显示出来只会误导。

## 五、管理端界面

### D7 「立即模拟调度」

**结论**：做，按真实延时真启动（可加速、可中止），呈现为进度视图。
**背景**：用户需要在真正接管之前确认"这批程序按这个顺序、这个间隔启动"是什么效果。
**后续**：时间轴视图被 D37 砍掉。

### D25 模板残留页

**结论**：建工程时就把模板自带的示例页删掉，导航壳暂时留空。
**背景**：模板页留着会被后来的人当成"待实现的页面"。

### D42 跨页数据不同步 + 遗留清理

**结论**：用 `ScanCacheService` 的来源级过期标记做局部刷新；删除 `\DelayStart` 文件夹清理代码。
**背景**：在一个页面里接管了条目，切到另一个页面还显示旧状态。

### D47 可添加的目标类型白名单

**结论**：移除 `.msi`，新增 `.ps1`（pwsh 优先宿主）；`LaunchTargetTypes` 是唯一事实来源。
**背景**：`.msi` 不是可执行文件，实测启动报 193 `BAD_EXE_FORMAT`。

### D48 编辑器的目标区

**结论**：「更换」按钮按目标形态分流；**UWP 没有工作目录概念，该项置灰**。

### D49 默认窗口尺寸

**结论**：1400×900 DIP（按 DPI 换算 + 工作区钳制 + 居中），最小 960×600（走 `WM_GETMINMAXINFO`）。
**背景**：`AppWindow` 的单位是**物理像素** —— 150% DPI 下直接写 1400 只会得到半屏窗口。

### D50 预设延时值与设置页分区顺序

**结论**：预设 `0/5/10/15/20/30/60`；「外观」分区提到最前。

### D51 延时页怎么分组

**结论**：按延时值分组，用已排序 Rows 的顺序切片。

### D52 分组的版式

**结论**：边框按组画 —— 子标题在框外，每组一张卡片。

## 八、自启动项守卫

> 起因：接管只是"软禁用"，它**不是一劳永逸**的 —— 应用升级后常把自己写回启用，新装的软件会偷偷加自启动，
> 被接管的应用卸载后会在清单里留下永远启动失败的孤儿条目。这三件事用户都不会主动发现，
> 需要一个会**自己跑起来看一眼**的角色。这一节的五条决策共同定义它。

### D74 自启动项守卫（机制与档位）

**结论**：新增独立的 `DelayStart.Guard.exe`，由登录触发的计划任务拉起，跑一次巡检即退出。一次巡检做四件事：①把**被应用写回启用**的已接管项重新软禁用（"写回纠正"）；②通报新增自启动项；③通报失效 / 孤儿条目；④把本次扫描结果写成**基线快照**供下次差集使用。档位 = `GuardMode`（`Disabled` / `OnceAfterLogin` / `Periodic`）+ `GuardMinutes`（白名单 10 / 30 / 60 分钟），**默认 `OnceAfterLogin` + 30 分钟**（2026-09-22 用户批复）。管理端**每次启动**按当前设置同步守卫计划任务：启用 ⇒ 补建或按当前档位重写；关闭 ⇒ 删除任务（`GuardTaskBootstrap`，语义对齐 `SchedulerTaskBootstrap` —— 用户原话是"跟调度器的计划任务一样进行检测复建，目的都是防丢失"）。
**背景**：守卫的失效尤其隐蔽 —— 它不常驻、不弹窗、平常不产生任何可见痕迹，任务被安全软件清掉或被误删之后，用户没有任何途径发现"保护已经没了"。
**为什么不是别的**：
- 不做常驻监控进程 —— 登录到关机一直跑，与调度端"轻量、不常驻、用完就退"的取向相反（D1/D14）。
- 不并入调度端 —— 调度端是 NativeAOT 纯 Win32，而守卫要经 Management 层用 `TaskScheduler` 与 `IShellLinkW`（COM），AOT 下运行必抛 `PlatformNotSupportedException`（R12）。
- 不让守卫自己维护"是否该运行"的状态 —— 直接读 `config.json` 的 `GuardMode`，单一事实来源；`GuardService.RunOnce()` 与入口都读它。
**代价与约束**：每次巡检是一次全量扫描（登录后一次 / 周期档位下每 30 分钟一次），属可接受的一次性开销。守卫**只做两件事**：纠正"用户已明确接管"的项、把变化通报给用户；它不做任何用户没同意过的系统改动（不自动清理、不自动接管）。

### D75 Guard 发布形态（非 AOT + 随管理端形态 + 同落点）

**结论**：Guard **不做 NativeAOT**；publish 形态**跟随管理端**（full 自包含 / slim 框架依赖），产物落在 `{app}` 根目录，与 `DelayStart.Scheduler.exe` / `DelayStart.LaunchBroker.exe` 同级（D3，用户批复）。
**背景**：Guard 走 Management 层，而 Management 的 `TaskScheduler` 与 `IShellLinkW`（`IPersistFile`）都是 COM。Core 有 `IsAotCompatible=true` 构建期守门，Management 没有 —— 它本来就只能跑 CoreCLR。
**为什么不是别的**：
- 不把 Guard 放独立子目录 —— 要与 App 各自维护一份运行时，卸载与清理路径翻倍。
- **slim 下 Guard 绝不自包含** —— `.NET apphost` 只要在自己目录里看到 `hostfxr.dll`，就把"运行时根"当成程序目录，于是框架依赖的管理端会报 `You must install or update .NET`，**哪怕机器上装着 10.0.12**（D64-1 已 1:1 复现）。往 slim 的 `{app}` 里塞自包含产物就是踩这条。
**代价与约束**：构建期守门 —— `installer/build-installer.ps1` 在 slim 形态下核对 publish 目录里**不得出现 `hostfxr.dll`**，出现即中止。这条 guard-rail 与 `installer/DelayStart.iss` 的 `PrepareToInstall` 防线是同一问题的两道保险。
开发期另有一条约束：守卫**非 AOT**，它的 exe 只是 apphost，搬进 App bin 时**必须整组四件**（`exe` + `dll` + `runtimeconfig.json` + `deps.json`），只拷 exe 是"找不到运行时"的空壳且编译期无提示。同步由 `DelayStart.App.csproj` 的 `CopyGuardBuildOutput` 钩子负责（`AfterTargets="Build"`，从守卫自己的 bin **拉**），因此 **`scripts/publish.ps1` 里 `build Guard` 必须排在 `build App` 之前**，且 App bin 的守卫四件已进产物核对清单（缺件 `exit 1`）。

### D76 防双启动（动态推导 + `Skipped` 语义）

**结论**：调度端在**首轮**（`Attempts == 0`）启动一个条目之前，先判断"该目标是否已经在跑"：可推导的（`.exe` / `.lnk` → 真实目标进程名）命中就跳过该条目并记 `Skipped`（Reason = 进程已存在），**不判失败**；不可推导的（`.ps1` 等脚本、AUMID、无扩展名）直接放行。进程名**运行时动态推导**（`LaunchTargetResolver` + `DuplicateLaunchPolicy`），不固化进配置。
**背景**：用户常开机后先手动启动某些程序，到点调度再启动一次就会得到两份实例（部分程序因此报"已在运行"或产生重复窗口）。
**为什么不是别的**：
- 不按 `DelayedItem.Path` 的文件名判定 —— 计划任务的 `Path` 常是 `cmd.exe` / `pwsh.exe` **包装器**，按 `Path` 取名会让包装器条目**每一轮都判"进程已存在"、永远不再启动**。
- 不把解析出的可执行名固化进 `DelayedItem`（配置 schema 变更）—— 用户改路径后固化值即失真（D2，用户批复）。
- 命中不标 `Failed` —— `Failed` 会推进失败连击、点亮托盘角标与失败横幅，而"进程已在跑"不是失败（D1 A，用户批复）。
**代价与约束**：只在首轮检查 —— 重试轮次里目标进程很可能就是上一次尝试拉起来的，再检查会把正常重试误判成"已在运行"。模块路径不可读时**不命中**（宁可多启动一次，也不误跳过）。

### D77 失效 / 孤儿检测与清理

**结论**：巡检把接管清单里"已经没意义"的条目分成两类通报 —— `Orphan`（系统里该启动项已被整个删除）+ `Missing`（启动项还在但目标程序已不存在）。守卫**只通报、不清理**；清理出口在管理端**「延时启动」页**（失效条目内联显示为"已失效"行，见 D81），用户确认后从 `config.json` 移除（`ConfigEditService.Remove`，**只改配置、不动系统**）。
**背景**：调度端会照着接管清单**无条件尝试启动**每一项。清单里留下已卸载软件的条目 = 每次登录都失败一次；而管理端此前只按主键关联显示扫描结果，孤儿条目在界面上**根本不存在**，用户无从清理。
**为什么不是别的**：
- 不自动清理 —— 自动删配置项属于"替用户做决定"（违反三原则之一）；且一次误判就会把好条目删掉。
- 不给 `Missing` 单独建视图 —— 对用户而言"这一条已经没用了"是同一件事，归并成一份通报。
- 不保留独立的「失效条目」页面（D81 起）—— 那个页面的内容与「延时启动」页高度重合，多一个入口只让用户多绕一次；内联显示还顺带解掉了"在延时页看得见、在失效页才删得掉"的割裂。
**代价与约束**：来源**整体失败时一律不判失效** —— 否则一次 ACL 拒绝或服务未启动会把整份清单报成"已失效"，诱导用户把好好的条目清理掉。

### D78 守卫入口自检（计划任务唯一入口）

**结论**：守卫有且只有**两个**入口 —— 计划任务拉起（唯一正常路径）与用户 / 调试手动运行。入口自检三步，任一不满足即静默退出：①**单实例互斥**（`Local\DelayStart.Guard`）命中 ⇒ 已有一轮在跑，直接退；②**非管理员身份** ⇒ 写 `guard.log` 一行"未以管理员身份运行（疑似手动双击启动）"并退出（**防用户双击**）；③配置里 `GuardMode = Disabled` ⇒ 同样静默退出（计划任务可能残留）。**通报载体已不在本节**：原来的 `TaskDialogIndirect` 模态提示框已被系统通知取代（D79），入口自检三步不受影响，`app.manifest` 也随之删除。
**背景**：守卫要改写 HKLM 下的 Run 项与第三方计划任务，**必须提权**；而它是 `asInvoker` 的普通 exe（`app.manifest` 里**不声明** `requestedExecutionLevel`），双击就能起。没有自检就会出现"起了但什么都做不了"的静默失败 —— 表现为"守卫生效了一半"，比完全不生效更难查。计划任务提权**不弹 UAC**（`RunLevel=Highest` + `Interactive`），是唯一能无条件拿到管理员的入口。
**为什么不是别的**：
- 不用 `MessageBoxIndirect` / 自绘小窗 —— 这条在 D78 落地时指的是"改用 `TaskDialogIndirect`"；那个方案本身也已在 D79 被推翻（模态框打断用户），最终形态是系统通知。
- 不为 Guard 单独维护一份"是否该运行"的状态 —— 直接读 `config.json` 的 `GuardMode`。
- 互斥检查放在提权检查**之前** —— 反过来会出现很吵的场景：用户连点几次双击，每次都先写一行"未提权"日志。
**代价与约束**：守卫现在是**纯托管 + WinRT** —— 原来的 `app.manifest`（comctl32 v6 依赖）随提示框一起删除，`pitfalls.md` 里"不得在清单里加 `requestedExecutionLevel`，否则双击门禁形同不存在"那条约束因此**作废**（清单本身没有了）；但"互斥检查必须排在提权检查之前"这条顺序约束仍然有效。另一处形态变化：守卫 TFM 提到 `net10.0-windows10.0.26100.0`（发 WinRT 通知需要平台版本才能拿到投影），因此它的 bin 路径带平台段 —— 与调度端（纯 Win32、无平台版本）不同，搬产物时别按调度端的路径套。

### D79 守卫的通报载体：系统通知（推翻 D78 的模态提示框）

**结论**：守卫发现变化时的通报改用 **Windows 系统通知**（右下角横幅 + 停留通知中心），点击通知经 `delaystart:` 协议拉起管理端并定位到相应页面。通知标题由**开始菜单快捷方式提供的应用名**显示为 `DelayStart`。这条**推翻** D78 里"提示框用 `TaskDialogIndirect` + `TDF_CALLBACK_TIMER` 自动关闭"的部分，D78 的入口自检三步不受影响（2026-09-22 用户批复：Windows 11 用系统内置通知、"能停留在里面"、点击拉起管理端；**Windows 10 也要右下角系统通知，不要屏幕中间弹出来，会打断用户**）。
**背景**：模态提示框在屏幕正中，会把用户从手上正在做的事里拽出来，并且**必须有人应答**才消失 —— 守卫是周期任务，这等于给用户安排了一个随时可能出现的打断。
**为什么不是别的**：
- 不做常驻等待点击 —— 通知由系统持有（发完即忘），守卫进程发完就退。`TaskDialogIndirect` 方案下守卫必须活着等 60 秒，与"跑完即退"的正向设计冲突，也是"上一轮没结束、下一轮被 `IgnoreNew` 挡掉"的来源。
- 不用 `activationType="foreground"` —— 那要求注册 COM 通知激活服务器（`INotificationActivationCallback`）并让管理端实现进程内类工厂；而发通知的守卫进程早就退出了，本来也没有活着的回调对象可指。用 `activationType="protocol"` + `launch="delaystart://<token>"`，点击即由 Shell 启动协议处理器。
- 不把 AUMID 直接当显示名 —— AUMID 字符串本身**不会**显示给用户；未打包应用要发通知，AUMID 必须先"存在"，唯一的存在方式就是开始菜单里有一个把它写进 `System.AppUserModel.ID` 的快捷方式，而那个快捷方式的名字才是用户看到的标题。所以"标题显示 DelayStart"与"通知能弹出来"是同一件事的两个面，都由 `ShellRegistrationService` 保证。
**代价与约束**：
- **注册是幂等的旁路，且绝不能抛异常**：管理端每次启动 + 守卫每次发通知前都调一次 `EnsureRegistered()`（写开始菜单快捷方式 AUMID + 写 `HKCU\Software\Classes\delaystart`）。注册失败只降级成"这次通知弹不出来"，绝不能让管理端起不来或让守卫巡检失败。
- 🔴 **同一 `Tag` + `Group` 的通知互相替换**（本实现用 `guard-change` / `delaystart`）：周期档位下每轮都可能"有变化"，不替换会让通知中心被同一件事刷满。代价是上一轮的具体条目名被覆盖 —— 那些条目在管理端里看得到，而通知中心被刷屏会让人直接关掉通知权限。
- 🔴 **卸载必须清掉协议键**：`installer/DelayStart.iss` 在 `CurUninstallStepChanged`/`usUninstall` 里 `RegDeleteKeyIncludingSubkeys` 删 `HKCU\Software\Classes\delaystart`（必须连 `shell\open\command` 子键一起删）。留着它就是一个指向已删除 exe 的 handler，用户点通知中心里的旧通知只会拿到系统报错框。
- ⚠️ **通知本身是尽力而为的**：系统通知被用户关掉 / 专注助手开着 / 组策略禁用都会导致它不显示，这些**不算巡检失败**。所以巡检结果必须始终落在 `guard.log` 里，通知只是附加通道。
- 守卫 TFM 因此必须带平台版本（`net10.0-windows10.0.26100.0`），`TargetPlatformMinVersion` 保持 `10.0.19041.0`。

### D80 守卫的通知策略（有变化时通知 / 从不通知）

**结论**：新增 `Settings.GuardNotifyMode`（`OnChange` / `Never`，**默认 `OnChange`**），入口在管理端**「设置 → 守卫 → 通知策略」**。它只管"要不要打扰用户"：两个取值下守卫都照常扫描、纠正写回、更新基线（2026-09-22 用户批复）。
**背景**：默认静默等于让守卫白跑 —— 它的全部价值就在于告诉用户"系统里多了 / 少了什么"；但周期档位下每轮都弹一次通知，对不关心的用户就是骚扰。
**为什么不是别的**：
- **不复用 `NotifyMode`（D15）** —— 那个描述的是"调度端完成后弹不弹进度面板"，两者的触发点（登录后巡检 vs 每次启动计划结束）与载体（系统通知 vs 应用内面板）都不同；合成一个字段会让"改了调度通知却把守卫也关掉"这种事故变得可能。
- **不复用 `GuardMode.Disabled`** —— `Disabled` 是"不巡检"，`Never` 是"巡检但不通知"；把两者合并会让用户在"不想被打扰"与"不要这个功能"之间被迫二选一。
- 不做三档（如"仅失效时通知"）—— 用户批复里只有两档，且"新增"与"失效"对用户的严重程度没有明显差异。
**代价与约束**：🔴 选「从不通知」时**必须**在 `guard.log` 里写一行"本轮有变化，但通知策略为「从不通知」，已跳过通报" —— 否则"策略为从不通知"与"本轮根本没跑"在日志里长得一模一样，排查时分不清。

### D81 失效条目并入「延时启动」页（删除独立页面）+ 转为手动

**结论**：删除管理端独立的「失效条目」页面（`StaleItemsPage` / `StaleItemsViewModel` / 导航项 / `items-stale` 标签）。失效条目在**「延时启动」页内联显示**：该行「启用」列不显示开关、改显示**「已失效」**文字（悬停给出原因），「操作」列换成 **「删除」** 与 **「转为手动」**。「转为手动」的前提是**目标文件还在** —— 目标程序已不存在时只剩下「删除」按钮（2026-09-22 用户批复）。
**背景**：失效条目本来就是"我配过、但它没用了"的延时条目，与「延时启动」页是同一批数据的两个视角；分成两页会出现"在延时页看得见、却要切到另一页才动得了"的割裂。
**为什么不是别的**：
- 不移除失效行 —— 静默丢弃会让用户以为配置丢失。留在列表里并标出来，用户才能看见"我配过这个，但它没了"并主动清理。
- **「删除」与「移出延时」不能合并** —— 后者会**恢复系统的原始自启动项**（它假设那个系统项还在、还归我们管），而失效行恰恰已经没有可还原的系统项（孤儿：系统项已被删除；`Missing`：目标程序已不存在）。合并文案等于让用户赌。
- **「转为手动」不做成"重新接管"** —— 系统项已经没了，无从接管。它的语义是"留着条目、切断系统锚点"：转换后条目与系统彻底脱钩，调度端照样按当前延时 / 参数 / 身份启动它。
**代价与约束**：
- 🔴 「转为手动」**必须重新生成主键**（`ItemKeyBuilder.ForManual()`）并清空 `Source` / `Scope` / `SourceKey` / `SourceDetail`。留着旧主键会让来源页把这条手动条目误判成"那个系统项仍被接管"，也会在系统项哪天回来时与真正的系统项撞主键。
- 🔴 转换会丢掉 `DelayedItem.OriginalState`（"把系统项还原回去"的依据）。可接受：用得上这条路的条目，其系统项已经不存在了，没有还原对象。
- 文件存在性在**界面侧与服务侧各查一遍**（`DelayRow.CanConvertToManual` 控制按钮显隐，`ConfigEditService.ConvertToManual` 落盘前再查一次）—— 服务层不假设调用方守规矩；判据是 `File.Exists` 而不是"扫描说它 `Missing`"，因为扫描结果可能来自上一次快照。
- 跨进程契约里 `stale` 令牌**保留**（已发出的通知里写着它），只是改映到「延时启动」页；`UiNavigationTarget.Delay` 与服务端选定的落点同理。

### D82 管理端提权改为「入口自提权」（修订 D20 的 manifest `requireAdministrator`）

**结论**：管理端 `app.manifest` 由 `requireAdministrator` 改为 `asInvoker`，管理员权限改由**进程入口自己申请**（`Program.Main` 的提权门）。三种走法：① 未提权 + **已有实例在跑** + 本次是"唤起"（`--goto-log` / `--goto-startup`，即通知点击与协议唤起）⇒ 只写一次性定位请求文件然后退出，**不申请提权、不弹 UAC**；② 未提权 + 没有实例可交（普通启动 / CLI 子命令）⇒ `runas` 重拉自己（弹一次 UAC，追加 `--elevation-attempted` 防重拉；CLI 等子进程并透传退出码）；③ 已提权 ⇒ 照旧。请求文件由**运行中的实例**用 `FileSystemWatcher` 收 —— D74 那个"只带载荷"的文件通道升格成"**载荷兼信号**"。2026-09-22 用户批复（原话：「按你的方案：入口自提权」）。
**背景**：D74 / D79 把守卫与调度端的通报改成系统通知，点击经 `delaystart:` 协议由 Shell 拉起管理端。而 `requireAdministrator` 的提权发生在**进程创建之前**（载入器决定，本程序一行代码都没跑），Shell 又必然以普通权限发起 —— 于是"管理端已经开着、只想让它前置并定位"这种最常见的情形也**必然先弹一次 UAC**。用户 2026-09-22 报的就是这个："管理端-延时启动 打开时，调度变化通知，点击通知，还是会弹出 UAC"。
**为什么不是别的**：
- **不用"协议指向一个降权中转器"**（另写一个不提权的小 exe 收协议再转交）—— 多一个进程、多一条安装与卸载路径；而它要解决的"跨完整性级别通信"在本方案里本来就有一个更省的做法（写文件 + 文件监听），中转器只是把同一个问题搬到另一个进程里。
- **不用常驻 broker**—— 收益仅是省掉一次 UAC，代价是每台机器多一个后台进程与一套生命周期管理，与"跑完即退"的正向设计相悖。
- **不改成"平时不提权、要写 HKLM 时再弹"**—— 违反 D20：核心链路 100% 需要管理员，按需提权只会把一次 UAC 拆成多次；而"用户以为禁用成功、实际静默失败"正是那条路上的事故形态。
- **不把 UAC 挪到"用户点通知"那一刻**—— 那就是现状，正是要修的东西。
**代价与约束**：
- 🔴 **不变量没放松，只是换了保证点**：图形界面与 CLI 业务**绝不**以非提权身份运行（D20）。所以提权门必须挡在**所有**业务分支之前，且 `--elevation-attempted` 必须在交给 `CliHost` 之前摘掉（它以连续两个减号开头，留着会被判成未知子命令、退出码 2、界面起不来 —— 同 `pitfalls.md` 十一那条）。
- 🔴 **跨完整性级别不能拿内核对象当信号**：中完整性进程打开高完整性事件时拿不到写权限（完整性级别默认"只挡写、不挡读"），而 `EventWaitHandle.TryOpenExisting` 的默认重载申请的正是写权限，且失败会被**静默折叠成 `false`**。于是：(a) 唤起信号改用请求文件 + 实例侧 `FileSystemWatcher`；(b) 存活探测下沉到 `OpenEventW(EVENT_SYNCHRONIZE)`（`Interop/InstanceProbe`）。**"文件当信号"还有一条附加好处**：文件不像事件那样过期即失，投递失败也不会丢单。
- 存活探测的误判方向是**安全**的：误判成"没有实例"只会白弹一次 UAC（被拉起的子进程在同级别里必然探测成功，拿到实例就只留请求文件退出，落点不会丢）。
- GUI 提权重拉**不等待**子进程（否则父进程要陪用户开到关窗，任务管理器里多一个看不见的进程）；CLI 等待并透传退出码。已知代价：提权子进程拿不到父进程的控制台，`--scan` 之类会开**新**的控制台窗口 —— 与改动前 `requireAdministrator` 的行为一致，不是本次引入的。
- ⚠️ **可见变化**：快捷方式 / exe 不再显示 UAC 盾牌；UAC 的**时机**从"启动瞬间"变成"入口判定之后"（次数不变：普通启动仍是一次）。
- 🔴 **卸载路径刻意不动**：`installer/DelayStart.iss` 继续用 `ShellExec('runas')` + `--result-file`（D61 真机验证过的路径）。`asInvoker` 之后理论上能退回 `Exec` 直接拿退出码，但那要在卸载流程里新增"UAC 被拒"与"父子退出码转发"两条真机没跑过的分支，收益只是少一次文件往返 —— 拒绝。
- 🔴 **`app.manifest` 是原样交给 `mt.exe` 的 XML**，注释里同样禁止出现**连续两个减号**（XML 规范）与 emoji / 非 BMP 字符。改了注释却报 `c1010070 Failed to load and parse the manifest`、且**不指出位置**，就是这两个原因之一（本次真踩过，见 `pitfalls.md` 十）。
- 新增跨进程令牌 `runs-log`（`UiNavigationTarget.RunsLog`）：`--goto-log` 的意图现在也要经文件通道表达（旧实现是"清空请求 + 发一个不带载荷的事件"）。新增令牌对旧读取方是安全的 —— 不认识的令牌只前置窗口、不切页。

### D83 调度完成通知与进度面板分离 + 通知中转器 `NotifyBroker`（N1–N12，2026-09-22 用户批复 D1–D5 全选 A）

需求稿 `docs/notify-broker-plan.md` 已退役（2026-09-22）：N1–N12 锚点定义移交 `design.md` FR-14.1，行为规格并入 FR-14 / 本条 / `development.md`。

**结论**：
- **通知与面板是两个不相干的功能**：调度全部结束后**无论面板是否显示**都按「通知策略」（`NotifyMode` 三档，语义纠正为"发不发系统通知"）发通知（N2/N5）；进度面板**仅手动弹出**（托盘左键 / 菜单），收尾不再自动弹（N4）；面板未显示时发完通知同拍退出（N6）。
- **通知走中转器 `DelayStart.NotifyBroker.exe`**（非 AOT + WinRT 投影，TFM 带平台版本，形态跟随管理端、与守卫同款四件套同步）：调度端写作业 JSON 后经**现有降权链**（外壳令牌 + CPWT）以中完整性拉起，fire-and-forget；broker `Show()` 后驻留 ~500ms 即退（N1）。`Tag=schedule-done` 与守卫 `guard-change` 互不替换；点击落 `delaystart://runs-log`（N11，D82）。
- **通知决策独立成纯函数 `NotifyDecision`**，`CompletionPolicy` 输入移除 `NotifyMode` / `FailedCount`，判定表退化为 `QuitImmediately` → 面板发起 → 面板可见 → 其余（D71–D73 基线表被本需求取代，编号保留）。
- **面板交互收敛**（N8–N10）：右上角去 ✕、去旧"置顶"，改单枚**钉** —— 默认失焦自动关闭（启动中仅收起；完成态收起即退出，D3=A），选中则高亮 + `HWND_TOPMOST` + 失焦不关；倒计时逻辑不变（钉住不暂停）。
- **D2=A**：菜单「跳过剩余任务并退出」也按策略发通知；**D4=A**：空计划无特判照策略发；**D5=A**：D18 旧气泡退役（`TrayIconHost.ShowBalloon` 删除）。

**为什么不是别的**：
- **不让调度端自己发通知** —— 双重死结：调度端提权运行，Win10/11 抑制提权进程的系统通知；且调度端 AOT 无 WinRT 投影（D24/D28）。二者决定了"谁来发"必须是中完整性的非 AOT 进程。
- **中转器不走 AOT + 手写 WinRT COM 激活** —— 体积省一点，维护风险极高；与守卫（D79/D75）同走"非 AOT + 投影 + 形态跟随管理端"。
- **不复用 `LaunchBroker` 加 `--notify` 模式** —— LaunchBroker 是稳定 AOT 组件且 TFM 无平台版本（发不了 WinRT 通知），为发通知改造它等于把降权链拖下水。
- **不保留"按策略自动弹面板"** —— 那正是"通知与面板混为一谈"的根源（语义错位：设置里叫通知策略、实际管面板）。

**代价与约束**：
- `NotifyMode` 枚举与 `config.json` **零迁移**（只换语义）；下拉文案换为「有失败时通知 / 总是通知 / 从不通知」（N3）。
- 通知是 best-effort（N12）：broker 缺失 / 拉起失败 / AUMID 未登记一律只记日志（`scheduler.log` / `notifybroker.log`），绝不阻塞、绝不拖垮调度退出。
- 作业文件走 `%TEMP%\DelayStart\notify\<Guid>\`（无标签对象按 Medium 处理，High 创建不挡 Medium 读写）；fire-and-forget 意味着调度端不删作业目录，由下一轮发通知时的陈旧清理（>1h）兜底回收。
- 中转器**绝不自行注册 AUMID / 快捷方式**（零 COM、零 shell 写入）；管理端从未启动过 → 通知发不出（仅日志），可接受。
- `CompletionPolicyTests` 判定表是**需求变更**而非回归破坏；D71–D73 编号保留作历史锚点。

### D84 安装器卸载/静默交互修正（2026-09-23 用户批复）

**结论**：
- **桌面快捷方式默认勾选**（修订 D62 的 `Flags: unchecked`，当时与用户预期相反）：GUI 与静默安装（`/SILENT` `/VERYSILENT`）都创建；静默排除用 `/MERGETASKS="!desktopicon"`。Inno 规则：静默安装不询问任务，直接按默认勾选态执行。
- **卸载"是否删除配置与日志"改为勾选框对话框**（`AskDeleteUserData`，自绘模态 `TSetupForm`）：在 `InitializeUninstall` 末尾（还原动作之后、进度窗之前）弹出，默认不勾 = 保留；点「取消」与"确定不勾"效果一致。（**D85 修订：废弃自绘窗体，改三按钮原生任务对话框并前置到还原之前**，见 D85）
- **静默卸载支持 `/DELETEDATA`**：传参即删配置与日志，未传一律保留 —— 删用户数据绝不静默发生。
- **还原失败分支三处 `MsgBox` → `SuppressibleMsgBox`**：普通 MsgBox 在静默卸载时不会被自动跳过，自动化卸载会卡死在无人值守弹窗上。默认值：UAC 被拒/无结果文件 = 继续卸载（不锁死用户）；还原失败（退出码非 0）= **中止**（无人能拍板"强行卸载"）。
- **顺手修复还原失败分支的 Result 逻辑 bug**：原 `if MsgBox(...) = IDYES then Result := True` 在 `Result` 已为 `True` 时是空操作 —— 点「否」也继续卸载，与文案相悖。改为默认中止、显式确认才放行。

**为什么不是别的**：
- **不把勾选框塞进卸载进度窗体（`UninstallProgressForm`）** —— Inno 卸载向导不支持插入自定义页，窗体出现时卸载已在跑，控件时机不可控；自绘模态对话框时机确定、行为可测。
- **不沿用 MsgBox 问"是/否"** —— 与安装向导的勾选交互不一致（用户明示想要勾选样式），且无法承载"默认不勾"的视觉暗示。
- **静默还原失败不默认"继续卸载"** —— 接管项没还原就删管理端 = 用户永久失去还原入口（D22 红线）；静默时无人确认，宁可中止。
- **不用 `{param:...}` 常量读参数** —— 它面向安装向导；卸载侧自扫 `ParamStr`（`CmdLineHasParam`）。

**代价与约束**：
- `CreateCustomForm` 签名 `(宽, 高, 是否居中向导内, 是否套用向导字体)` 返回 `TSetupForm`（照官方 `Examples\CodeClasses.iss`，签名记错会在 ISCC 编译期报 "Invalid number of parameters"）；静默检测函数名是 **`UninstallSilent`**（没有 `IsUninstallerSilent`）。
- 程序文件已不在（exe 缺失）时 `InitializeUninstall` 提前退出，不会弹处置对话框 —— 数据保留，可接受。
- GUI 卸载多一次点击（对话框），换来显式知情权。

### D87 调度周期采用「引用」模型（FR-15，2026-09-23 用户批复：1–6 全选 A）

**结论**：
- 条目只存 `ScheduleCycleId`（**引用**，不是星期组合快照）；周期定义在 `config.json` 顶层 `cycles`，不属于任何条目。
- 内置 5 档 = `b:everyday` / `b:weekdays` / `b:weekends` / `b:legal-workday` / `b:legal-holiday`，**不可改不可删、不出现在设置页**（只在延时弹窗里挑）；自定义档 = `c-` 前缀 + 8 位十六进制随机串。
- 引用语义的三条兜底约束：**被引用的周期不可删**（删除按钮置灰 + 悬停写明"N 个条目正在使用"）、**引用失效回落「每天」**（+ warn 日志）、**改前在面板副标题告知影响面**。
- 🔴 **不存在"不选周期"状态**：空值一律按「每天」处理。想让条目不跑就关条目级「启用」开关 —— 空周期不是表达这件事的地方。
- 判定只用 Core 的 `ScheduleRulePolicy.Matches`；接入点唯一（`SchedulePlan.Build(items, cycles, today, calendar)`，由 `SchedulerEngine` 调用）。**管理端绝不自算**，只把判定结果翻成中文文案。

**为什么不是快照（🅐）**：快照（挑中即拷一组星期进条目）没有引用完整性负担，但"改一次规则要逐条改"在本产品的使用场景里是常态（用户描述的就是"上一休一 / 周末班"这类会被反复微调的规则）。选引用、把负担交给三条约束，是用户接受的取舍。

**为什么删不掉就别删（而不是"自动改成每天"）**：删一个被引用的周期时，"那些条目应该变成什么"没有正确答案 —— 自动改回每天越过了用户意图（他可能根本不想让它每天跑），自动关闭则是静默停摆。让用户先改走别的周期，是唯一不需要替他做决定的做法。

**代价与约束**：`ScheduleRuleKind` 枚举**不再持久化**（只由解析器产出）；星期位掩码必须经 `WeekdaySets` 换算（`WeekdaySet` 周一 = bit0，与 `DayOfWeek` 周日 = 0 **不一致**，手写位移就是 bug）；`ConfigService.Normalize` 负责兜底（空/重复 id、非法位、失效引用），配置版本不升（旧配置零迁移 → 默认「每天」，行为与升级前一致）。

### D88 节假日数据：源、本地格式、下载降级与自动化边界（FR-15，2026-09-23）

**结论**：
- 数据源 `holiday-cn`（`NateScarlet/holiday-cn`），按用户指定顺序逐个降级：`raw.githubusercontent.com` → `fastly.jsdelivr.net/gh/` → `cdn.jsdelivr.net/gh/`（国内直连 GitHub 常被拦/丢包，两个 CDN 是同一份数据的镜像）。
- 本地**归一化**存储（与第三方 schema 解耦）：`%LOCALAPPDATA%\DelayStart\holidays\{year}.json`，camelCase，`workdays` / `restDays` 用 ISO 日期串（给人看），`MinimumEntryCount = 20`。
- **判定三级降级**（NFR-y）：命中数据 → 数据说话；该年有数据但当天未列 → 按星期规律（静默）；该年无数据 / 文件坏 → 按星期规律近似**且界面可见**（徽标 `≈` + 悬停写明缺哪年）。
- 🔴 **HTTP 200 ≠ 有数据**：国务院通常 11 月才公布次年安排，那期间源文件存在但 `days` 为空 —— 这条路径报「尚未公布」（走通知），**不是错误**；且校验不过时**绝不覆盖**本地已有数据。
- **自动化边界（NFR-x）**：下载只出现在 `DelayStart.Management` 的 `HolidayCalendarUpdateService`。启动后的自动检查（`HolidayAutoCheckService`）默认**开**，但触发条件收得很窄 —— 仅"当年数据不可用 + 节流期已过"，节流记录 `holidays\.last-check` 里的键是**上次尝试的结局**（`HolidayCheckThrottle`）三档：`Updated`（拿到数据并落盘，安静期以"那份数据仍在可用位置"为前提，前提不成立就**立即重来**）/ `NotPublished`（上游明说未公布）→ 7 天 / `Failed` → 1 小时。
  - 🔴 第一版把时间戳写在**发请求之前**，等于一次网络抖动就让用户静默 7 天、界面上连个"什么时候试过"都问不出来。**记账必须记结局，不能记"我试过了"**（2026-09-23 真机修复，`pitfalls.md` 十七）。旧版单行 ISO 时间戳按"失败"读。
  - 🔴 第二版只有"成功 / 失败"两档，于是出现了第二种静默：**下载成功过、文件后来在本地被改名**，节流拿"成功"记账、再也不会去补，年份行显示"未下载"而开关是开的。现在 `Updated` 的安静期以"那份数据仍在可用位置"为前提 —— 调用方只在本地没有可用数据时才会问节流，所以"记录说已获取 + 走到节流判据"就是"数据丢了"，没有等 7 天的理由（2026-09-23 第二次真机，`pitfalls.md` 十七）。中间那代的 `ok` 标记按 `Updated` 读。
  - 🔴 全程可见：进度与上次结果上报单例 `HolidayUpdateStatus`（设置页 `x:Bind` 直接绑），开关打开即触发一次（用户动作，绕过节流），后台补齐成功发一条应用内通知。判据：一个后台任务如果用户在界面上问不出"它跑没跑"，那它就是缺陷。

- **导入**的年份取自**文件内容**（`year` 字段）而不是文件名；**两种格式都收**（2026-09-23 用户批复 13）：`holiday-cn` 的原始格式与本地归一化格式都能直接导入，写盘前必过 `HolidayCalendarStore.TryValidate`。
  - 🔴 判据是顶层有没有 `days` 数组（原始格式必有、归一化格式没有），不做试探性反序列化。
  - 🔴 **下载与导入共用同一份归一化实现**（`HolidaySourceConverter`）：两处各写一套，迟早会出现"下载能落盘、导入被拒收"这种同一份数据两种结局的分叉。要求用户把上游文件自己转成归一化格式，等于把「离线机器该有一条活路」这件事又堵回去 —— 他没有这个工具，也没有这个义务。
- **到期提醒**：11 月 1 日起、次年无数据、且确有启用的条目在用法定两档 → 延时页顶栏 Informational 横幅（不弹窗）；没有条目用法定两档时不提示（那只是噪音）。

**为什么下载不放在调度端/守卫端**：那两个进程登录即跑、必须离线可判定（判定输入只能来自本地文件）；在它们里面联网意味着"网络慢"会变成"开机卡"甚至"判定不出来"。管理端是人看着用的界面，网络失败可以当场说清楚。

**为什么自动检查默认开**：条件极窄（等价于"首次安装补齐当年"），收益是用户不必知道有这个开关；关掉之后本地数据照常使用，只是不再自动补。

**代价与约束**：`Core` 新增 `WeekdaySet` / `ScheduleCycle` / `HolidayCalendar(Store)` / `ScheduleRulePolicy` / `ScheduleCycleResolver`；本地日历是**唯一一个跨三层共用**的数据文件（管理端写、调度端与守卫端只读），因此读取侧一律"失败即降级"；自动检查的节流文件与数据同目录（用户清空目录 = 时间戳一起失效，下次启动重新补）。

### D89 周期跳过的条目进运行日志，但「不启动」的语义不变（FR-15.26，2026-09-23 用户要求）

**结论**：
- `SchedulePlan` 的产出从"一个列表"扩成 `ScheduleOutcome { Entries, SkippedToday }`：`Entries` 按发起顺序 = 原来的计划；`SkippedToday` 是**启用了、但今天不在其周期内**的条目（同样按发起顺序）。`Build(...)` 退化为 `BuildWithSkipped(...).Entries`，历史调用点与既有用例零改动。
- 调度端把 `SkippedToday` **追加在计划项之后**写进 `RunRecord.Items`：`State = Skipped`、`Reason = "今天不在启动周期内，未启动"`、`Delay` 照填、`LaunchedAt` 留空（"没有发起时刻"是该字段的既有语义）。
- 🔴 **只进日志，不进 `_items`**：它们没有到点时刻，不参与 `Tick` 与收尾判定，也不进进度面板的计数。面板回答"这次跑得怎么样"，日志回答"今天该不该跑"，两者不许混。
- 🔴 **全部启用条目都被跳过时照样写一份归档**（外加实时状态 `current-run.json`），然后走 FR-5.10：不建托盘、不进消息循环、不弹面板，通知照旧按策略发（默认策略下不发），静默退出。
- `Enabled = false` 的条目**既不进计划、也不进日志** —— 两层过滤的次序不变（FR-15.4）：算进去等于把"你自己关的"报成"周期决定今天不启动"。

**为什么不是在计划里"留个坑位标跳过"**：让跳过项进 `_items` 会同时污染三处口径 —— `PlannedCount` 与面板 `TotalCount` 对不上行数；"跳过 N 项"的通知文案把"今天不该启动"与"用户点了跳过"算成一件事；收尾判据多一类永远满足的条件。日志是唯一需要它存在的地方，就只让它出现在那里。

**代价与约束**：`RunItemState.Skipped` 现在有**三种来源**（用户放弃 / 防双启动命中"进程已存在" / 今天不在周期内），三者只能靠 `RunItemResult.Reason` 区分；`FailureStreakService` 只认 `Failed`，所以跳过项既不推进也不中断连击 —— 与"该条目不在这次记录里"完全等价（老行为就是它不在记录里），失败统计零变化。`_items` 与 `_record.Items` 的下标不再一一对应，运行侧改走**先建 `planned` 列表**再两边各自引用，不再靠"两边下标对齐"。

### D90 当年无节假日数据时的降级：静态星期近似 + 可见提示（FR-15，2026-09-23 用户批复）

**结论**：法定两档在该年**无数据**（未下载 / 下载失败 / 官方尚未发布）、或数据文件损坏时，**按常规星期规律近似判定** —— 法定工作日 → 周一至周五，法定节假日 → 周六日；且这件事**必须可见**（列表徽标 `≈` 后缀 + 悬停写明缺哪年、`scheduler.log` warn、设置页提示条）。

**为什么不是"不匹配（不启动）"**：数据缺失期间条目**静默停摆**，用户会以为软件坏了 —— 而"为什么今天没启动"是所有 bug 里最难查的一类。
**为什么不是"匹配（每天）"**：那会让"只在周末跑"的条目在周三跑起来，越过用户意图。
**为什么选近似**：长期看它只是"国务院没改历法时的最好猜测"，短期错漏只可能出现在调休日。"No data"不是"不做事"的借口，但也不能是"替用户猜" —— **近似 + 把近似这件事说破**，是这两条原则唯一的交点。

**代价与约束**：降级链共四级 —— ① 该年数据里命中 → **数据说话**（调休补班日覆盖星期规律）② 该年**有**数据但当天未列出 → 星期规律（静默）③ 该年**无**数据 → 星期规律 + **必须可见** ④ 文件坏 → 同 ③ + error 日志，且**不得抛异常打断登录**。🔴 第 ② 级**必须存在**：`holiday-cn` 只收"特殊日"，普通周末根本不在 `days` 里，砍掉它就会得出"2026-09-23（普通周三）不是法定工作日"的荒谬结论。🔴 **兜底方向一律更宽松，绝不更严格**。

### D91 「法定节假日」= 官方日历上的休息日全集（FR-15，2026-09-23 用户批复）

### D94 自定义周期不允许"一天都不选"（FR-15，2026-09-23 用户批复）

**结论**：七宫格为空 → 点「保存」**不关面板、不落盘**，在下方红字报错；选中任一天后红字立即消失。空周期**不是合法状态**。

### D96 周期 id 用字符串字面量（FR-15，2026-09-23 用户批复）

### D97 改一个被引用的周期时，把影响面说全（FR-15，2026-09-23 用户批复）

**结论**：编辑被 N 个条目引用的周期时，在面板**副标题**提示数量 + **条目名列表**（"3 个条目正在使用：xxx、yyy、zzz，保存后同步生效"）。

**为什么**：引用语义最大的风险就是"改一处、悄悄影响一片"。只给数量，用户知道自己动了几条；**把名字列出来**，用户才知道动的是哪几条 —— 而这正是按下「保存」之前唯一该确认的事。

**代价与约束**：副标题就是副标题，**不进面板正文**（FR-15.16）—— 面板里只许有名称 + 七宫格两样输入。删除侧同理：行右侧写明「N 个条目在用，禁止删除」（FR-15.14），悬停再给操作指引；两个方向都必须回答"我动了谁"。

### D98 运行日志的结果列改纯中文，不带符号前缀（FR-8，2026-09-23 用户批复 23）

**结论**：`RunItemRow.StateText` 一律**纯中文**——`成功` / `失败` / `跳过` / `启动`（兜底档 `未执行`）。**不用 emoji，也不用 ✓ ✗ ◌ 这类符号。**

**为什么**：这一列此前是「✓ 成功」「✗ 失败」「◌ 跳过」，并且为了"看起来等宽"给 ◌ 补过一个空格 —— 方向就补错了。根因是这些符号**根本不在同一套度量里**：✓(U+2713) 与 ✗(U+2717) 大致 1 em，◌(U+25CC)、·(U+00B7) 更窄，emoji（✅❌）则是彩色的、约 1.2–1.4 em 宽（WinUI 会把它们 fallback 到 Segoe UI Emoji 渲染）。**逐字符试探字宽是个填不满的坑**；拿掉符号后四档都是两个汉字，字宽天然一致。

**代价与约束**：要表达"跳过"与"失败"的差别用**颜色**（`IsFailed`），不要回头再加字形。"启动中"⇒"启动"是用户点名的措辞，状态语义不变（仍是 `Launching`）。

**待用户拍板**：`Waiting` 档沿用原文案「未执行」（三个汉字，比其他档宽一个字）—— 没擅自改词。

### D99 延时弹窗里的周期胶囊不分组（FR-15，2026-09-23 用户批复 23）

**结论**：延时编辑弹窗「调度周期」一节里，内置 5 档与自定义周期**排在同一排胶囊里**，取消中间的分隔线与「我的周期」小标题。

**为什么**：这一屏要回答的是"这条哪天启动"。"内置还是自建"只决定**将来能不能改删**，那是设置页那一列才需要强调的差别；在弹窗里把它做成视觉分组，等于让一个次要属性占掉一层层级。

**代价与约束**：内置 5 档顺序仍固定在前（`BuiltinCycleIds.Ordered`），自定义接在后面、「＋ 新建周期」收尾 —— **用顺序表达来源，不再用分组表达来源**。

### D100 设置页的「延时」「周期」两节改成可折叠列表（FR-9 / FR-15，2026-09-23 用户批复 23）

**结论**：两节都变成"节头一张边框 + 展开后**每条一张独立边框**"；节头右端是「＋ 新建延时 / ＋ 新建周期」加一颗展开三角，**默认收起**；点节头左半边（整块）或三角都能展开/收起。延时的新增改成**弹窗**（弹窗内校验，失败不关窗）。周期的列表**把内置 5 档也列出来**：编辑 / 删除置灰，右列「**内置周期，禁止删除**」。

**为什么**：① 两节各自可能攒下十几行，常驻展开会把节假日数据 / 调度 / 守卫全挤进滚动区 —— 而节头那行已经把"这一节是干什么的"说完，**收起不等于藏信息**；② 用户需要一个地方看见"总共能选哪些周期"，而不是只有打开延时弹窗才知道；③ 延时的内联"输入框 + 添加"在只有三个控件时够用，但两节版式统一后，**弹窗才是那个不随列表变长而变形的形态**。

**代价与约束**：
- 折叠状态存在 **ViewModel**（`IsDelaySectionExpanded` / `IsCycleSectionExpanded`），不读控件的 `IsChecked` —— 节头左半边与三角是两个入口，只有一个真值才不会出现"点了左边、三角还朝下"。
- 内置档与自定义档**共用同一个 `CycleRow`**（新增 `IsBuiltin` / `CanEdit`），不另起一套只读控件：给内置档单独做一套，等于把"能不能改"这一条属性放大成一整套视觉差异。
- `CycleRow.DaysText` 改由调用方翻好传入（法定两档要显示「按国务院通知」），行对象不再认识 `CycleInfoProvider` —— 一处翻好，避免两处各翻一遍而分叉。
- 列表顺序固定为"内置在前、自定义在后"，不做按名排序：排序会让新加的周期插进列表中间，用户下次进来找不到刚建的那个。

### D101 设置的「延时」「周期」两节：节头 = 整行按钮 + 纯图标三角（FR-9 / FR-15，2026-09-23 用户批复 24）

**结论**：节头里那颗三角**不再是 `ToggleButton`**，改成一枚跟着 ViewModel 变的 `FontIcon`（无背景 / 无边框 / 无自己的悬停态）；展开与收起的唯一入口是包住**整行**的透明 `Button`（标题、描述、图标都在它的内容里，点哪儿都算）。「＋ 新建延时 / ＋ 新建周期」移出节头，成为**第一条子内容**；展开后的子内容**左右各内收 16**，一眼看出是上级的子内容。

**为什么**：① 用户原话——"右侧三角是纯文字/图标并不是按钮（你当前有点像按钮）"，`ToggleButton` 自带背景与悬停态，与"装饰性指示符"的语义打架；② 三角不再是入口之后，"点了左边、三角还朝下"这类分叉在结构上**不可能发生**，`SyncSectionToggles` 那层回写补丁随之删除；③ 节头同时扛"标题 + 描述 + 新建"三件事时，哪件是主操作只能靠猜 —— 拆开后节头只回答"这一节是什么"，添加是子内容里的第一件事。

**代价与约束**：
- 新建多了一层"先展开"才能点到。可接受：新建是一次性动作，而这两节的默认形态是收起、天天要看的是"当前配置是什么"。
- 折叠状态仍只存在 ViewModel（`IsDelaySectionExpanded` / `IsCycleSectionExpanded`），不以控件的 `IsChecked` 为准 —— 现在只剩一个入口，但真值仍只能有一个。
- 三角与标题必须落在**同一个** `Button` 的内容里（而不是"标题按钮 + 旁边一颗图标"）：分开摆就会出现"点得到标题、点不到三角"的死区。

### D102 预设延时的行形态与文案（FR-9.2，2026-09-23 用户批复 24）

**结论**：每行左侧显示 **「登录后 n 秒」/「登录后 n 分 m 秒（xxx 秒）」**（新增 `DisplayText.LogonDelayOf`，与既有 `DelayOf` **并存**）；右侧是「**设为默认**」「**删除**」两个按钮，**当前默认那一行**把「设为默认」换成绿色的文字「**当前默认**」。原先"点整行 = 设为默认"的整行 `ToggleButton` 取消（连带 `UncheckOtherPills` / `OnPresetChecked` / `OnPresetUnchecked` 一起删）。

**为什么**：① 用户填进去的是秒数，回到列表里只看见「2 分 30 秒」——中间那一步换算不该由用户做，所以补「（150 秒）」（分钟整点也补：「2 分（120 秒）」，否则用户会以为整点那种没被记录）；② 整行可点的代价是行内其余控件都要防冒泡，而"点这一行会发生什么"界面上一个字都没说，摆明按钮，代价与收益都写在脸上；③ 默认行不摆一颗点了没用的按钮（`IsDefault` / `IsNotDefault` 两个真值，`x:Bind` 不支持取反，界面不做判断）—— 判据仍在行对象里，界面照画。

**代价与约束**：
- `LogonDelayOf` 与原 `DelayOf` **刻意分成两个方法**：后者是列宽敏感的短文案（延时列 / 周期徽标同行 / 分组标题都用它），不该被括号里的秒数撑开。**改一处必须想清楚改的是哪一份。**
- 0 秒显示「**登录后立即**」（2026-09-24 用户批复，历经「登录后 0 秒」→「立即」→「登录后立即」）：同列每一行都在回答"登录后多久"，保留「登录后」前缀、把 0 换成「立即」，既说清"不等待"，也不让这一行在纵向上落单。列表页的延时列（`DelayOf`）仍是裸的「立即」—— 那一列按列宽排版，整列本来就没有前缀。**`DelayGroup.Header`（延时启动页分组标题）的 0 秒也改为「登录后立即」**（同期批复，此前是「立即启动」）：同一批文案里三处 0 秒口径就此收敛为两档 —— 列宽敏感的延时列给裸的「立即」，其余两处（预设行、分组标题）都带「登录后」前缀。分组标题单列一个分支而不是拼 `DelayOf`，是为了避开拼出来的「登录后 立即」中间那个空格。
- 中间那一格用**固定列宽 88px**，让「设为默认」按钮与「当前默认」文字共用一个格 —— 两种形态下最右的「删除」才对齐。给字符加空格是凑不出对齐的。
- 删除预设的二次确认文案跟着变成「确定删除「登录后 30 秒」吗？」—— 同一行两处叫法必须一致。

### D103 列表列头一律左对齐（FR-7 / FR-8，2026-09-23 用户批复 24，批复 25 扩到全部列头）

**结论**：列头**统一左对齐**，做法是**把 `HorizontalAlignment="Center"` 去掉**（`TextBlock` 默认 `Stretch` + `TextAlignment=Left` 就是左对齐）。

- 批复 24 先改用户点名的几处：总览「最近一次开机调度」（延时 / 结果）、延时启动（延时 / 身份 / 启用 / 顺序）、服务与驱动（启动类型 / 状态，**同一处表头管两页**）、运行日志（延时 / 结果）。
- 批复 25 扩到**全部列头**，把上一轮留着没改的补齐：总览「时间 / 程序」、延时启动「# / 程序 / 操作」、自启动项「状态 / 操作」、运行日志「程序 / 说明」。

**为什么**：行内那些值本来就是左对齐的，列头居中会让**同一列出现两个基准**：列头看着像标题、值像另一回事。列头该和它管的那一列**起点对齐**。

**代价与约束**：上一轮刻意只改点名处、把「同一表头里有的居中有的靠左」留在明处并**问过用户要不要一起改** —— 用户批复"全部左对齐"。教训是：**同一张表头里混两种对齐不该作为"等待确认"的稳定态交付**，它本身就是一处视觉缺陷，问到就答、答完一次改净。

### D104 设置页可展开节头：卡面长在按钮上，悬停整张卡片响应（FR-9 / FR-15，2026-09-23 用户批复 25）

**结论**：`SectionHeaderButtonStyle` 从"透明按钮 + 外层 `Border` 画卡面"改为"**按钮自己画卡面**" —— 按钮的 `Background` = `CardBackgroundFillColorDefaultBrush`、`BorderBrush` = `CardStrokeColorDefaultBrush`、`BorderThickness=1`、`CornerRadius=7`、`Padding=16,14`，样式 `BasedOn="{StaticResource DefaultButtonStyle}"`；XAML 里两处节头（延时 / 周期）**删掉外层 `Border`**。

**为什么**：真机反馈"鼠标移上去只有文字那一块变色"。根因不是视觉状态没生效，而是**高亮的作用面只有按钮那么大**：外层 `Border` 的 `Padding` 把按钮从卡片边缘往里推了 16 / 14，按钮自身的 `CornerRadius`（4）又比卡片（7）小一圈 —— 悬停色填在卡片内部一小块圆角矩形里，看起来就是"文字区域变了色"。把卡面交给按钮后，`PointerOver` 会同时改写 `ContentPresenter.Background`（`ButtonBackgroundPointerOver`）与 `BorderBrush`（`ButtonBorderBrushPointerOver`），**整张卡片连描边、圆角一起响应**；`Pressed` 同理。

**代价与约束**：① 必须 `BasedOn="{StaticResource DefaultButtonStyle}"`，自己从头写一套会让悬停/按下/禁用三态全丢（`DelayPage.RowButtonStyle` 是同一手法，先前已跑通）；② 静态那几项（卡面/描边/圆角/内边距）必须与别的卡片**逐项一致**，否则同一屏里两种卡片长得不一样；③ 不能用"给 `Border` 加指针事件改画刷"的写法绕：那是把控件已经做对的事在 code-behind 里重做一遍，还得自己管 Entered/Exited/CaptureLost。

### D105 列头与行的左右内缩：容器归零，列头只取「之间」那几层（FR-7 / FR-8，2026-09-23 用户批复 26；2026-09-24 批复 27 并入运行日志页外层分组容器）

**结论**：列表的左右内缩只由**两个**来源决定 —— 卡片 `Border` 的 `Padding` 与**行** `Grid` 的 `Padding`。

- 三个列表页（自启动项 / 服务·驱动 / 运行日志）的行容器样式（`ItemRowStyle` / `RunRowStyle`）`Padding` 由 `8,0` 改为 **`0`**；
- 这三处**列头**的 `Grid.Padding` 由 `28,8,28,·` 改为 **`12,8,12,·`**（= 行 `Grid` 的 12）；
- 总览「最近一次开机调度」的小表**补上 `ItemContainerStyle`**（新增 `RowItemStyle`：`Padding=0` / `Stretch` / `MinHeight=0`），列头保持 `4,·`（= 行 `Grid` 的 4）；
- 延时启动页（`ItemsControl` + 分组卡片，无 `ListViewItem`）本来就是对的：列头 28 = 内层卡片 8 + 行 `Grid` 20，**不动**。
- **运行日志页的外层分组列表**（`ItemTemplate` 是 `Expander`）同样没挂容器样式，整组（组标题 + 表头 + 行）比卡片边框多缩 12 —— 一并归零（2026-09-24 用户批复 27）。这一层在列头与行**之上**，两者都吃它，所以归零不改变相对基线，只是让分组标题落到与其它列表页同一条内缩上。

**为什么要改（两个各自独立的偏差）**：

1. **列头把不属于自己的内缩算进来了。** 注释里那条公式「Border 8 + ListViewItem 8 + 行 Grid 12 = 28」描述的是**行**的起点，却被写成了**列头**的 `Padding` —— 列头与行之间只隔着一个 `ListViewItem`，卡片 `Border` 的 8 是两边**共同**吃掉的，不该在列头里再补一遍。结果列头比行多缩 8（36 vs 28）：同一列上下两个起点，而且行文字离卡片边 28px，看着"左边莫名一块空白"。
2. **总览小表的 `ListView` 从来没挂 `ItemContainerStyle`**，于是落到 WinUI 默认 `ListViewItem`（`Padding 12,0`、`MinHeight 40`）：行内容比列头多缩 12（32 vs 20），行高还被撑到 40。

**公式（以后按它算，不再逐页手摸）**：

> 列头 `Grid.Padding` 的左右 = 「列头与行**之间**」所有层的内缩之和。
> 容器一律 `Padding=0`，于是它就等于**行 `Grid` 的左右内缩**。

**代价与约束**：① 行容器 `Padding` 一旦不为 0，就必须把它加进列头，且**只能加一次**（列头在容器外）——与其每次提醒自己，不如把容器钉死在 0；② 去掉容器内缩后行的左右内缩从 28 收到 20（总览 32 → 20），卡片里的内容整体更贴边，这是"列头与行同一条基线"的必然结果，两侧一起移、静态观感不变形；③ `ListView` 漏挂 `ItemContainerStyle` **没有任何编译期提示**，而默认值与自定义值差 12 / 40 —— 新加列表页时**先挂样式再写列头**。

### D106 拖放接收器的幂等判据：看「现在的过程」，不看「见过的 HWND」（R10，2026-09-24 用户批复 28）

**结论**：`FileDropReceiver.EnableSingle` 去掉 `OriginalProcs.ContainsKey(hwnd)` 这道门，改为**先读窗口当前的过程**——等于自己的过程指针就直接返回（真幂等），否则把当前过程记进 `OriginalProcs[hwnd]`（**覆盖写**）并重新子类化。

**背景**：真机反馈"偶尔往窗口里拖文件完全没反应"。根因是 **HWND 会被系统回收复用**：判据问的是"这个句柄值我见过吗"，而它该问的是"这个窗口现在的过程是不是我的"。复用命中时新窗口被跳过子类化，而 `DragAcceptFiles` 在早退**之前**已经执行（`WS_EX_ACCEPTFILES` 真的设上了）—— 资源管理器照发 `WM_DROPFILES`，消息落进默认过程。整条路径**零异常、零日志**。

**代价与约束**：
- 🔴 `WindowSizing.EnforceMinimum` 里**逐字相同**的写法**不动**：它防的是另一件事 —— 本项目有两个窗口过程子类化器，去掉那道门会让后调用者把过程再压一层、"原过程"记录指向对方 → **过程链成环 → 栈溢出**。它只在启动时对主窗口调一次、主窗口 HWND 终身不变，所以无害。
- 按 HWND 记账的表只能当**缓存**看，是否成立必须当场核对；表只增不减是有意的（子类化不卸载），HWND 复用后旧值会被覆盖，实际几十条就平台化。
- 判据顺序即语义：**先问"现在对不对"，再决定要不要动手**；"我做过没有"不能代替"现在对不对"（`pitfalls.md` 二十）。

### D107 局部重扫的三类数据必须同进同退（FR-1.4，2026-09-24 用户批复 28）

**结论**：`NavigationView.FooterMenuItems` 新增一项「关于」（tag `about` → `Views/AboutPage.xaml` + `ViewModels/AboutViewModel.cs`）。版式**照抄总览**：`ScrollView` 里一个 `Padding="32,8,32,40"` + `MaxWidth="1000"` + `HorizontalAlignment="Stretch"` 的容器（页头随内容滚动、内边距计入限宽）。内容四节 —— **应用**（名称 / 版本 / 一句话定位 + 「复制诊断信息」）、**运行环境**（应用版本 / .NET 运行时 / 操作系统 / 运行身份 / 架构，`stc:SettingsCard` 只读行）、**数据位置**（配置 / 数据 / 日志 / 安装目录，各带「打开」按钮）、**开源**（项目主页 + MIT + 联网说明）。

**代价与约束**：① `Clipboard.SetContent` 走系统剪贴板（与自启动项页同款），被别的进程占着会抛 —— 报错而不重试；② 「打开项目主页」在提权进程里 ShellExecute 一个 http 地址，浏览器**可能**继承提权（现代浏览器一般会自行降权重启）；要彻底规避得用调度端那套 `DeElevatedProcessLauncher`，为一条"打开网页"引入跨进程启动器不划算；③ "值本身是常量"的成员必须写成**带初始值的自动属性** —— `=> 常量` 会撞 CA1822，改 `static` 又绑不上 `x:Bind`（`pitfalls.md` 二十一）。

### D111 Inno `AppId` 保持原值（2026-09-24 用户询问后定案）

**结论**：`installer/DelayStart.iss` 的 `AppId={{8F4C0B6A-2C1D-4E3B-9A5F-DELAYSTART001}` **保持不变**。

**背景**：上架 winget 牵出发布者口径（D6），顺带被问到"这个不是 GUID 的 `AppId` 当初怎么来的、要不要一起换掉"。

**当初怎么来的**：2026-09-19 首版安装器脚本**手写**的仿 GUID 串（`commit 2ca0129`）。Inno 对 `AppId` 的要求只有"任意字符串、≤127 字符、不要中途改"，**没有"必须是 GUID"** —— 规范形状的 GUID 只是社区惯例（VS 的安装项目模板会给一个）。

**为什么能改但选择不改**：`AppId` 决定两件事 —— ① 卸载注册表键名（`AppId` + `_is1`）；② 写进 `unins000.dat`，后续安装据此判断能否**追加到同一个**卸载记录。中途改的后果（Inno 官方 FAQ 口径）：安装程序不再认得旧版本 → "设置 → 应用"里出现**两个条目**，并生成一份新的卸载记录文件，而旧条目的卸载器仍指向同一个安装目录。**收益是零**：winget 不要求 `ProductCode` 是 GUID（见上），不换也能把 `ProductCode` 写全。

**未生效的备选**：换成真 GUID（`New-Guid` 生成）并同步 manifest 的 `ProductCode` —— 只在"尚无任何公开装机量"时才值得做（现在 v0.2.0–v0.3.1 已经发出去过）。

### D112 守卫任务「每次启动重写」会吞掉本次会话的巡检（2026-09-24 用户上报后定案）

**结论**：`GuardTaskRegistrar.RegisterOrUpdate` 在写入前**先逐字段比对现有任务定义**，完全一致则跳过 `RegisterTaskDefinition`，保留已武装的登录触发器；只有定义确实变了才重写。

**背景**：用户发现开机登录后打开管理端，守卫当天一次都没跑（guard.log 自昨日 14:44 后零记录），任务计划程序里「上次运行时间」显示的是管理端重写任务的时刻、而「下次运行时间」卡在昨天。`CreateOrUpdate` 每次都重建触发器。

**根因**：守卫触发器是 `LogonTrigger` + `InitialDelay`（登录后 N 分钟、一次性）。登录事件在会话里**只能消费一次**；管理端启动期重写任务 = 用全新 `LogonTrigger` 替换定义，而此时登录事件已过去，新触发器在本会话内永远等不到下一次登录 → 该次巡检被静默丢弃。周期模式同理（重复序列锚在触发器激活上）。

**正确做法（F1）**：写入前比对现有定义的关键字段 —— action 路径与工作目录、Principal（Interactive/Highest/UserId）、触发器（Delay、Repetition.Interval、UserId）、六项 Settings（ExecutionTimeLimit=0、DisallowStartIfOnBatteries/StopIfGoingOnBatteries/RunOnlyIfIdle/RunOnlyIfNetworkAvailable=false、MultipleInstances=IgnoreNew）、`RegistrationInfo.Description`。**全部一致 → 跳过写入**；任一不符（档位调整 / 安装目录迁移 / 任务被改坏）→ 真正重写。D74「缺失即补建 / 关闭即删除」语义全部保留，只去掉了"每次启动无条件重写"。

**附带发现（已记 pitfalls 二十二）**：此前 `GuardTaskRegistrar` 注释称 `CreateOrUpdate` 幂等、保留运行统计 —— **被真机证伪**：重写会重置触发器、且「上次运行时间」等统计会被覆盖成重写时刻（假成功）。

**验证**：`dotnet build -c Release` 0 警告 0 错误；`scripts/test.ps1` 643/0。新增判定「同会话内第二次同步应返回 `NoChange`」锁住 F1（原 `FakeGuardTaskRegistrar` 改为：同模式同档位的重复请求返回 `false`，模拟"定义已最新"）。

### D113 调度计划任务「每次启动重写」同样会重置登录触发器（F1 调度端镜像，2026-09-24 用户要求）

**结论**：把守卫 F1（D112）的"定义一致就跳过重写"机制**原样应用到调度端** —— `TaskRegistrationService.RegisterOrUpdate` 在写入前先逐字段比对 `\DelayStartScheduler` 的现有定义，完全一致则跳过 `RegisterTaskDefinition`，保留已武装的登录触发器与运行统计；只有缺失或定义确实变了才重写。

**背景**：用户明确指示"调度器的任务计划也应该同样处理，已经存在并且一模一样的情况下，也不要重建调度器计划任务"。守卫因重写而静默吞掉巡检（D112）是这轮修复的起因；调度任务的触发器同样是 `LogonTrigger + InitialDelay`（登录后 N 秒、一次性），重写会重置该窗口并覆盖「上次运行时间」等统计——虽不像守卫那样直接吞掉一次巡检，但统计失真、且毫无必要地触碰系统状态。

**正确做法（与 D112 同源，仅少"重复"一项）**：比对字段 = action 路径与工作目录、Principal（Interactive/Highest/UserId）、触发器（Delay = 登录后 N 秒、不重复、UserId）、六项 Settings（ExecutionTimeLimit=0、DisallowStartIfOnBatteries/StopIfGoingOnBatteries/RunOnlyIfIdle/RunOnlyIfNetworkAvailable=false、MultipleInstances=IgnoreNew）、`RegistrationInfo.Description`。**全部一致 → 跳过写入**；任一不符 → 真正重写。`SchedulerTaskBootstrap.EnsureSchedulerTask` 改为先取 `IsRegistered` 再调 `RegisterOrUpdate`（返回是否真正写入），按（已存在, 已写入）组合记不同日志。D68「缺失即补建」语义全部保留，只去掉了"每次启动无条件重写"。

**与守卫的差异**：调度端是固定规则、不随设置变化，所以**不存在"档位调整"这种触发重写的情形**；这也意味着相同定义下每次启动都不应触碰它。守卫的 `IsDefinitionUpToDate` 多了 `Repetition.Interval`（周期模式）一项，调度端没有。

**验证**：`dotnet build -c Release` 0 警告 0 错误；`scripts/test.ps1` 644/0（新增 `EnsureSchedulerTask_UpToDateDefinition_SkipsRewriteAndLogsNoRebuild` 锁住"已存在且一致则跳过重写"；原 `FakeSchedulerTaskRegistrar` 改为 `RegisterOrUpdate` 返回 `bool`，已写过分相同定义时返回 `false`，并增 `WriteCount` 区分"调用次数"与"实际写入次数"）。

### D114 守卫与调度的计划任务注册机制合并为一份（2026-09-24 用户要求）

**结论**：新增纯数据 `ScheduledTaskSpec`（任务名 / 路径 / 描述 / exe / 工作目录 / 登录延迟 / 重复间隔 / 文案简称）与机制层 `ScheduledTaskGateway`（`internal sealed`，不进 DI，D3 批复），守卫与调度两条计划任务的注册 / 逐字段比对 / 删除实现收敛为**唯一一份**；`GuardTaskRegistrar` 与 `TaskRegistrationService` 瘦身为**策略适配器** —— 只决定"此刻该有什么样的任务"（守卫：档位→`GuardSchedulePlan`→Spec、`Disabled`→删除；调度：固定 Spec），把 Spec 交给 Gateway 执行。两个接口（`IGuardTaskRegistrar` / `ISchedulerTaskRegistrar`）、两个 Bootstrap、测试替身、全部调用方与 DI 注册**零改动**。

**背景**：D112 / D113 落地后，两份 `IsDefinitionUpToDate`（各约 70 行）与注册主流程逐字拷贝并存，守卫注释里写着"这六项与 `TaskRegistrationService` 一模一样，改一处要改两处"；用户明确指示"不要重复实现高度类似的代码"。有利条件：测试只依赖接口与 Fake，两个实现类没有任何直接单测，重写实现层对 644 个用例零冲击。

**取舍**：备选 A（模板方法基类）否——继承耦合，守卫"Disabled→删除"这类策略在基类里难安放，Fake 也无法复用；备选 C（单类实现双接口）否——违背 D74 的接口分离理由（守卫随设置变化、Disabled 即消失，调度是"必须存在的固定规则"）。选 B（组合式 Spec + Gateway）：机制单份、Spec 纯数据、策略留在适配器。

**文案微调（仅调度侧异常消息，属改善）**：异常统一为"注册/删除调度计划任务失败"（原"注册/删除计划任务失败"缺主语）；exe 缺失统一为"调度程序不存在"（原"调度端程序不存在"）。其余日志与守卫侧文案逐字不变。

**真机首验修正（同日）**：用户以 `scripts\all.ps1` 产物实测发现"每次启动都重写"仍发生。只读探针取证：任务库落盘把 Principal 账户名规范化成 **SID**、库读回 `Principal.UserId` 是**裸名** `guyue`（丢 `MSI\` 前缀），与写入值 `MSI\guyue` 的字符串比对永不命中——F1 被架空。修正：Principal 与触发器的 UserId 比对改经 `SameAccount`（全名/裸名/SID 统一归一化成 SID 再比，pitfalls 二十四），并给测试程序集开 `InternalsVisibleTo` 补 8 例纯函数单测（652/0）。教训：新机制的"自写自读"往返保真必须在真机验证，单测与 Fake 覆盖不到系统服务的规范化行为。

**验证**：`dotnet build -c Release` 0 警告 0 错误；`scripts/test.ps1` 652/0（D114 本体未改用例 644/0；账户归一化修正后含新增 `SameAccount_NormalizesSidAndNameForms` 8 例）。

### D116 运行时数据按进程归堆 + 守卫巡检结构化归档（2026-09-24 用户批复）

**结论**：三件事一次落地 —— ① 目录重构：`state\`、`runs\` 撤销，调度端数据收进 `scheduler\`（`current-run.json` 与 `archive\<runId>.json`），守卫巡检新增结构化归档 `guard\inspections\<yyyyMMdd-HHmmss>.json`（保留 30 份）；② 守卫日志页数据源从 guard.log 文本解析切换为巡检归档，按次分组（D3），总览守卫卡切归档（D5），guard.log 文本双轨保留（D4）；③ 旧数据由管理端启动时一次性迁移（`RuntimeDataMigrator`），几个版本后移除。

**验证**：`dotnet build DelayStart.slnx -c Release` 0 警告 0 错误；测试 668/0（删 `GuardLogReaderTests` 12 例，新增 `RuntimeDataMigratorTests` 6 例、`GuardInspectionStoreTests` 6 例、`GuardRunSummaryTextTests` 3 例、`GuardServiceTests` CompletedAt 1 例）。
