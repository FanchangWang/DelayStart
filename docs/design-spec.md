## 一、产品定位

| 项 | 内容 |
|---|---|
| 中文名 | **延时启动管理器** |
| 英文名 | **DelayStart** |
| 一句话 | 把开机时一股脑抢占资源的自启程序，改成按你的节奏、错峰、延时启动。 |
| 副标语 | 不删除任何原始配置 · 全部可一键还原 |
| 目标用户 | Win11 用户，开机被 20+ 个自启程序拖慢，但又不舍得直接禁用某个程序 |
| 核心价值 | ① 全位置扫描（注册表 3 处 + 2 个启动文件夹 + 计划任务 + UWP）<br>② 软禁用，随时可还原<br>③ 延时可编排，处理程序间的启动依赖 |
| 与"直接禁用自启"的区别 | 禁用 = 永远不启动；延时启动 = **照常启动，只是晚一点**。适合"我需要它，但不想它开机就跟我抢资源" |

**明确的非目标（不做）**：
- ❌ 不做启动项清理/优化评分（那是另一个产品）
- ❌ 不做系统服务延时接管（服务用系统原生的「自动（延迟启动）」）
- ❌ 不碰内核驱动启动顺序
- ❌ 不修改 Winlogon / Userinit / Shell（只读展示）

## 二、信息架构

左侧 `NavigationView`，共 6 个顶层模块 + 「自启动项」下的 5 个子视图。

```
┌ 延时启动管理器 ────────────────────────────────────┐
│                                        [☀/🌙] [—]  │
├────────────────┬───────────────────────────────────┤
│ ⌂  总览         │                                   │
│ ▤  自启动项  13 │                                   │
│    ├ 全部       │          内容区                    │
│    ├ 注册表   6 │                                   │
│    ├ 启动文件夹 2│                                   │
│    ├ 计划任务  3│                                   │
│    └ UWP 应用  2│                                   │
│ ⏱  延时启动   4 │                                   │
│ 🛡  系统启动项   │                                   │
│ ▤  运行日志     │                                   │
│ ⚙  设置         │                                   │
├────────────────┴───────────────────────────────────┤
│ 调度任务：已创建 · 登录后 3 秒触发        [详情]     │
└────────────────────────────────────────────────────┘
```

导航栏为什么把「来源」做成子项：这个软件的差异化就是「扫得全」。把 5 个来源平铺在导航上，用户一眼就知道程序查了哪些地方、各自查到几个 —— 比藏在筛选器里强。

### 搜索框为什么从导航栏挪进页面

**原始设计是错的。** 导航栏顶部放一个「搜索启动项」输入框，效果是：用户在「延时启动」页打字，页面被强制跳转到「自启动项」页 —— 用户的上下文被抢走。

改成**页面内搜索**，两处各自独立、各搜各的：

| 位置 | 搜什么 | 匹配字段 |
|---|---|---|
| 自启动项页工具栏 | 系统里已有的自启动项 | 名称 / 路径 / 命令行参数 / 值名或文件名 / 所在位置 / 来源类型 |
| 延时启动页工具栏 | 已接管的条目（含手动添加） | 同上 |

规则：
- 只过滤**当前页**的列表，绝不跳页、绝不改 `state.src`
- 搜索状态与页内筛选器（状态 / 排序）叠加生效，互不干扰
- 输入框有内容时右侧显示清空按钮；清空后恢复完整列表
- 「延时启动」页处于搜索状态时，「上移 / 下移」按钮禁用（顺序是全局语义，在过滤视图中调整会产生歧义），并在表下给出说明
- 空结果时给「清空搜索」按钮，不是干巴巴一句"没有数据"

导航栏顶部不再有任何输入控件。

## 三、逐页 UI 文案

### 页面 1 · 总览

**标题**：总览
**副标题**：开机自启动一览，以及延时启动的执行计划

**统计卡（4 张）**

| 卡片标题 | 数值示例 | 辅助文案 |
|---|---|---|
| 已扫描自启动项 | 15 | 其中 2 项已禁用 · 4 项为系统组件 |
| 已接管延时启动 | 5 | 系统自启动 4 项 · 手动添加 1 项 |
| 开机加载窗口 | 1 分 00 秒 | 从登录到最后一个程序启动 |
| 开机调度任务 | 已就绪 | 登录后 3 秒触发 · 以最高权限运行 |

> **计数口径**：`已扫描自启动项` 只数系统里扫到的条目（不含手动添加）；`已接管延时启动` 数所有被接管的条目，并拆出手动添加的数量。两个数字口径不同是刻意的 —— 第一个回答"系统里有什么"，第二个回答"我接管了什么"。

**「开机启动时间轴」卡片**
小标题：开机启动时间轴
说明：登录后各程序的启动时点
（横向时间轴，横轴标尺：`登录` → `10s` → `30s` → `60s` → `1min`，节点为程序图标+名称）

**「调度任务」卡片**
- 已就绪状态：`调度任务已创建` / `触发器：登录时，延迟 3 秒` / `运行身份：最高权限（不弹 UAC）`
- 缺失状态（警示色）：
  > ⚠ **尚未创建开机调度任务**
  > 延时启动不会生效。需要创建计划任务，在登录后唤起调度器。
  > [立即创建] [稍后再说]

**「最近调度」卡片**
小标题：最近一次开机调度
- 记录行：`✅ 微信 · 30s · 成功` / `❌ pot 翻译工具 · 60s · 启动失败（文件不存在）`
- 无记录时：`暂无调度记录，重启后在此查看`

**操作区**：`[刷新扫描]` `[立即模拟调度]`

> **「立即模拟调度」是刻意放在首屏的**。延时配置写完必须重启才能验证，体验很差。这个按钮让用户当场看到效果（0.5 倍速播放时间轴 + 真的启动程序），是开发调试和用户验收的双赢。

### 页面 2 · 自启动项

**标题**：自启动项
**副标题**：共 13 项 · 已接管 3 项 · 已禁用 1 项

**工具栏**（从左到右）
`[🔍 搜索名称 / 路径 / 值名]` `[来源 ▾]` `[状态 ▾]` `排序 ▾` … `[刷新扫描]`
批量模式下额外出现：`已选 3 项` `[批量延时启动]` `[批量禁用]` `[取消选择]`

> **「手动添加」按钮不在这里** —— 自启动项页的职责是「列出系统里已有的东西」，不是创造新东西。手动添加只存在于「延时启动」页。
>
> 由此引出一条数据边界：**手动添加的条目不进入本页**。它没有注册表值可以软禁用，也没有来源可以恢复，混进本页会让「禁用」这个动作变得无意义。本页的提示条里写明了这一点。

**筛选器文案**
- 来源：`全部来源` / `注册表` / `启动文件夹` / `计划任务` / `UWP 应用`
- 状态：`全部状态` / `已启用` / `已禁用` / `已接管` / `已失效`
- 排序：`按来源` / `按名称` / `按状态`

**列表行（示例）**

```
┌───────────────────────────────────────────────────────────────────────┐
│ [W图标] 微信                                      ● 已接管    [⋯]    │
│         C:\Program Files\Tencent\Weixin\Weixin.exe  -autorun          │
│         注册表 · HKEY_CURRENT_USER\...\Run · 值名 Weixin               │
│         延时 30 秒 · 普通用户                [移出延时]               │
├───────────────────────────────────────────────────────────────────────┤
│ [☁图标] OneDrive                                  ● 已启用    [⋯]    │
│         C:\Program Files\Microsoft OneDrive\OneDrive.exe  /background │

```

**状态徽标文案与配色**

| 徽标 | 含义 | 配色 |
|---|---|---|
| `已启用` | 系统会正常自启 | 中性灰描边 |
| `已禁用` | 已通过软禁用标记阻止自启 | 警示黄 |
| `已接管` | 原自启已禁用，改由本程序延时启动 | 强调色实心 |
| `已失效` | 路径不存在 / 任务已被删除 | 危险红 |
| `受保护` | 系统组件，不可修改 | 灰色 + 锁图标 |

**内嵌说明文案**（列表顶部常驻一条轻量提示条）
> 这里的「禁用」与「移出延时」都是**软禁用**：不会删除注册表值，也不会移动文件，随时可以还原。<br>
> 本页只列出**系统里已经存在**的自启动项。手动添加的程序属于调度任务而非系统自启动项，只出现在「延时启动」页。

**行内操作菜单 `⋯`**
- `打开文件位置`
- `复制命令行`
- `查看来源详情`（弹出：完整注册表路径 / 任务 XML / AUMID / 快捷方式目标）
- `在任务管理器中查看`
- →（已接管项）`编辑延时设置`

**空状态**
- 筛选无结果：`没有匹配的启动项` / `试试更换筛选条件或清空搜索关键词`
- 该来源本就为空：`此位置没有自启动项` / `注册表 ...\Run 下没有找到任何条目`

## 三之二、延时配置编辑器（弹窗）

「自启动项」页的 `[延时启动]`、「延时启动」页的 `[手动添加]` 和 `[编辑]`，**共用同一个弹窗组件**，靠"是否已绑定系统来源"分叉。这样用户只需要理解一套交互。

### 4 种进入方式 → 3 种形态

| 入口 | 目标程序 | 可编辑字段 | 底部主按钮 | 第 4 块内容 |
|---|---|---|---|---|
| 自启动项页 `[延时启动]` | **只读**（由系统项绑定） | 参数 / 延时 / 身份 | 加入延时启动 | 接管对象 |
| 延时启动页 `[编辑]`（系统来源） | **只读** | 参数 / 延时 / 身份 | 保存修改 | 接管对象 |
| 延时启动页 `[编辑]`（手动条目） | 可更换 | 名称 / 参数 / 工作目录 / 延时 / 身份 | 保存修改 | 系统影响 |
| 延时启动页 `[手动添加]` | 可选择 | 名称 / 参数 / 工作目录 / 延时 / 身份 | 加入延时启动 | 系统影响 |

分叉的唯一依据是**这条记录有没有系统来源**。有来源 → 路径由系统项决定，不允许改；没来源 → 路径是这个记录的全部意义，必须能改。

### 设计要点

- **步骤编号 ①②③④** 把长表单切成 4 块。原来的弹窗是一堆无标题的控件堆叠，看不出结构。
- **目标程序是唯一的大控件**。它是这一步的全部信息量，用整块虚线拖放区承接，而不是一个普通输入框 + 一个浏览按钮。选中后原地变成「图标 + 名称 + 路径 + [更换]」，视觉上"填好了"这件事一目了然。
- **第 4 块是"会动到系统什么"的交代**。有系统来源时列出资源位置和接管动作（强调软禁用）；手动条目时反过来强调**不动系统任何东西**。两种情况下用户最关心的都是同一件事：我这次操作会不会搞坏系统。所以这块不能省。
- **底部摘要是活的**：`将在 登录后 30 秒 以 普通用户 身份启动`，随延时/身份选择实时更新。用户不用回去逐项核对就能确认最终结果。
- 弹窗宽度 620px（比确认类弹窗宽），容纳拖放区。

### 各块文案

| 块 | 标题 | 副标题 |
|---|---|---|
| ①（可选文件） | 目标程序 | 拖入文件或点击选择 |
| ①（只读） | 目标程序 | 由系统自启动项绑定，不可更改 |
| ② | 延时时间 | 相对登录时刻的时间点 |
| ③ | 启动身份 | — |
| ④（系统来源） | 接管对象 | — |
| ④（手动条目） | 系统影响 | — |

**弹窗标题 / 副标题**

| 场景 | 标题 | 副标题 |
|---|---|---|
| 手动添加 | 手动添加延时启动 | 选择一个程序，由本程序在登录后延时启动 |
| 加入系统项 | 加入延时启动 | 来自「注册表」，加入后原自启动项将被软禁用 |
| 编辑系统项 | 编辑延时设置 | 修改已接管条目，原自启动项保持软禁用 |
| 编辑手动项 | 编辑延时设置 | 手动添加的条目，不关联任何系统自启动项 |

- 空态主文案：`点击选择程序，或把文件拖到这里`
- 空态副文案：`支持 .exe / .lnk / .bat / .cmd / .msi`
- 文件类型白名单是硬性的：`.exe` `.lnk` `.bat` `.cmd` `.msi`。不接受 `.dll`、文件夹、文档。

### 「移除延时」确认弹窗（分两种文案）

| 条目类型 | 正文 | 主按钮 |
|---|---|---|
| 系统来源 | 该程序的原始自启动项将恢复为**你接管前的状态**。<br>下次登录时它会按系统原本的方式启动，不再受本程序控制。 | 移除并恢复 |
| 手动添加 | 该条目是**手动添加**的，不关联任何系统自启动项。<br>移除后只删除本程序里的这条配置，**系统的任何设置都不会被改动**。 | 移除条目 |

### 页面 3 · 延时启动

**标题**：延时启动
**副标题**：共 5 项（含手动添加 1 项）· 最后一个在登录后 1 分 00 秒启动

**工具栏**：`[🔍 搜索已接管的程序]` `[列表 | 时间轴]` … `[立即模拟调度]` `[导出]` `[导入]` `[＋ 手动添加]`

**列表视图**

| 列 | 内容 |
|---|---|
| 顺序 | `1` `2` `3`，同延时内可上下调序 |
| 名称 | 带图标 |
| 命令 | 路径 + 参数 |
| 延时 | `登录后 30 秒`（可点击内联修改） |
| 身份 | `普通用户` / `管理员` |
| 来源 | `注册表 HKCU` / `用户启动文件夹` / `计划任务` / `UWP` / `手动添加` |
| 操作 | `↑` `↓` `编辑` `移除` |

搜索状态下的行为：
- 只影响列表内容，不影响页头统计（统计反映全局）
- `↑` `↓` 置灰，表下补一句：`搜索状态下暂时无法调整顺序。`
- 时间轴视图同步过滤；无匹配时显示 `没有匹配的条目。清空搜索框可恢复完整时间轴。`

**常驻提示条**
> 延时时间是**相对登录时刻**的时间点，不是累加。同一时间点的程序按列表顺序依次发起启动。
> 如果 B 依赖 A 先启动，请给 B 设置**更大**的延时值。

**时间轴视图**
横轴：`登录` → `10s` → `30s` → `60s` → `1min` → `2min`
节点按延时值定位，同一时点的多个条目纵向堆叠并标注发起顺序。

## 四、调度端（登录后执行的轻量进程）界面

> **完整设计已拆分为独立文档：`docs/scheduler-design.md`。**

**原方案已推翻**：早期设计是在屏幕右下角放一个常驻进度面板。**这个设计是错的** —— 调度器的存活时长等于最长延时（用户可设数十分钟），而这恰好是用户刚登录、正在干活的时段。登录后抢屏的窗口，无论做得多精致都是错的。

**新方案（一句话）**：调度端**没有主窗口**，只有一个托盘图标。默认完全隐形；用户悬停看一行摘要、点击弹出面板（失焦即关）；调度结束后发系统通知，**默认只在有失败时发**；点击通知打开管理端「运行日志」页并定位本次运行。

信息通道分 5 级，默认停在 0 级（静默），任何升级都必须由用户主动触发（失败提醒除外）：

| 级别 | 通道 | 用户动作 |
|---|---|---|
| 0 | 完全静默 | — |
| 1 | 托盘图标 + 悬停 tooltip | 主动悬停 |
| 2 | 托盘弹出面板 | 主动点击，失焦即关 |
| 3 | 系统通知（默认仅失败） | 系统弹出，可点击 |
| 4 | 管理端「运行日志」页 | 主动打开完整程序 |

**两条硬技术约束**（详见 `scheduler-design.md` 第五节）：

1. 调度器是管理员权限进程，Windows 通知平台**不支持 elevated 进程发真 Toast**；NativeAOT 也用不了 WinRT / Windows App SDK 的通知 API。只能用托盘气泡通知（`Shell_NotifyIcon`）。
2. Win11 上气泡通知**不进通知中心**（Win10 会留，Win11 变瞬时）。所以通知**不能是唯一通道**，必须有兜底 —— 管理端总览页的「上次运行结果」横幅 + 完整运行日志。

### 6.1 D17 批复说明：失败由用户处理，软件不代劳

**批复：不自动处理。** 原建议 C（连续 3 次失败后自动交还自启动）被否，理由充分且比原方案更正确：

1. **自动交还自启动 = 软件在用户不知情时改了系统状态**，直接违反本项目"全部可逆、且由用户掌控"的核心原则。
2. **失败原因多数不归本软件管**（程序被卸载、被杀软拦截、路径变更）。自动恢复自启动只是把问题从"不启动"变成"启动失败弹错误框"，还顺手把用户设的延时取消了 —— 问题没解决，配置先丢了。
3. **静默改配置比明示失败更糟**。用户宁可看到一条一直存在的警告，也不愿某天发现"我明明设了延时，怎么没生效"。

**改为三条约束：**

| 约束 | 内容 |
|---|---|
| 保持接管 | 失败项**始终**保持软禁用 + 接管状态，下次登录按原延时继续尝试。软件永不自动修改该项的系统状态 |
| 提醒必须持续 | 失败提示不能只出现一次。托盘角标保留、管理端横幅常驻，直到用户显式处理（见 `scheduler-design.md` 第八节） |
| 出口只有一个 | 管理端横幅上提供 `[移出延时启动]` 直接跳转到该条目的移除确认流程（系统条目走"移除并恢复"），由用户点击完成 —— **软件只给路径，不做决定** |

### 7.3 疑问 1：延时时间怎么选？

**答：预设快选 + 自定义输入，两者都要；预设值本身可在设置里改。**

| 方案 | 判断 |
|---|---|
| 只给定死几个值 | ❌ 不行。延时是强场景相关的 —— 有人要 5 秒，有人要 15 分钟 |
| 只给自由输入框 | ❌ 不行。多一步敲键盘，90% 的情况都是 10/30/60 秒 |
| **预设按钮 + 自定义输入框** | ✅ 主路径一次点击，兜底任意数值 |
| **再加：预设值可在设置里编辑** | ✅ 成本极低，解决个性化 |

所以弹窗长这样：`[登录后立即] [10 秒] [30 秒] [60 秒] [2 分钟]` + `自定义 [__] 秒`，右下角一行小字 `预设值可在「设置」里改`。

**不做**：完整的多选/拖拽式预设编辑器 —— 过度设计，一个逗号分隔的文本框足够。

### 7.4 疑问 2：最大延时上限 —— 你说得对，我的设计有缺陷 ✅ 已改

**原设计的错误**：把「最大延时上限」做成了 10 分钟，这是**用配置去限制调度能力**。用户想设 1 小时延时，软件把它卡在 10 分钟 —— 那就不是"延时启动"，是"启动失败"。这个设置项存在的意义被搞反了。

**修正为两件事，彻底分开：**

| 概念 | 性质 | 归属 |
|---|---|---|
| **单条目延时上限** | 纯输入校验，防呆（防止误填 999999） | 设置项，默认 24 小时，可选"不限制" |
| **调度器驻留时长** | **算出来的**，不是设出来的 | 只读展示 = `max(所有条目的 delaySeconds)` + 面板保留时间 + 启动开销 |

举例（当前配置）：
```
SyncTool         10 秒
微信              30 秒
Epson Scanner    60 秒   ← 最长延时
AutoHotkey       60 秒
─────────────────────────
调度器驻留      60 + 3 + 2 ≈ 1 分 05 秒
```

设置页里这一行是**只读的**，并明确写「调度器会在最后一项启动后自动退出，不会常驻后台」。用户设 1 小时延时，驻留时长就是 1 小时，软件不会、也不该拦着 —— 但要让用户事先知道。

**唯一需要用户配置的"时间"** 是：全部启动完成后进度面板再保留几秒（默认 3 秒）。这才是真正需要人来定的那个值。

### 7.5 搜索框从导航栏移到页面内 ✅ 已改

原设计的错误：导航栏顶部一个全局搜索框，用户在任何页面打字都会被强制跳转到「自启动项」页。**抢走用户的上下文**是明确的 UX 缺陷，不做辩解。

改为两处**页面内搜索**（自启动项页 / 延时启动页），各自独立、只过滤当前页、不跳页、不改来源筛选。完整规则见第二节末「搜索框为什么从导航栏挪进页面」。

放弃全局搜索的理由：本程序总共十几到几十条记录，且导航栏已经按来源分好组、每项带计数。为了"快速定位某程序"而引入一个会抢焦点的全局控件，收益不抵成本。

### 7.6 手动添加 / 编辑弹窗重做 ✅ 已改

原实现只是个 Toast 占位（`原型未展开`），等于没有设计。现在补全，并按「有没有系统来源」分成 3 种形态，共用一套布局：

- **4 个编号步骤**（目标程序 / 延时时间 / 启动身份 / 系统影响或接管对象），把长表单结构化
- **目标程序做成整块拖放区**，选中后原地变「图标 + 名称 + 路径 + [更换]」
- **底部活摘要**：`将在 登录后 30 秒 以 普通用户 身份启动`，随选择实时更新
- **手动条目和系统条目在第 4 块和第 1 块上明确分叉**：手动条目能换文件、写明"不动系统任何东西"；系统条目路径只读、写明"写入软禁用标记，可还原"

完整规范见第三节之二。

同时落定的数据边界：**手动添加的条目不属于系统自启动项，不进入自启动项页**。它只在「延时启动」页出现，不参与"已扫描自启动项"的计数。
