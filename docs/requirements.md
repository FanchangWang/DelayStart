## 一、项目背景与目标

### 1.1 要解决的问题

Windows 的登录自启动机制是**全有或全无**的：一个程序要么在登录瞬间和所有兄弟程序一起抢资源，要么被彻底禁用。现实后果：

- 登录后头 60 秒磁盘 IO 打满、CPU 占满，桌面要等一分多钟才能用
- 用户不想禁掉这些程序（禁了就忘了，或者偶尔要用），但也不想让它们挤在同一个瞬间
- 任务管理器只能"启用/禁用"，不能"晚 30 秒再启动"

### 1.2 产品目标

**扫描所有自启动位置 → 软禁用（不删数据）→ 由独立的调度进程按延时启动。**

三个不可妥协的原则：

| 原则 | 含义 |
|---|---|
| **全部可逆** | 禁用是"软禁用"（写 `StartupApproved` 标记 / `task.Enabled=false` / UWP `State=0`），**绝不删除注册表值、绝不移动用户文件**。任一条目都能一键还原到接管前的状态 |
| **判定可靠** | 延时是"相对登录时刻的绝对时间点"，不是累加。软件必须准确告诉用户"这个程序会在登录后第几秒启动"，而不是"大概" |
| **不替用户做决定** | 启动失败时软件只提醒、不自动改系统状态（D17）。所有会改变系统行为的动作，出口都在用户手上 |

### 1.3 技术目标

| 目标 | 指标 |
|---|---|
| 管理端冷启动 | < 2 秒（WinUI 3 自包含的合理区间） |
| 调度端冷启动 | < 0.3 秒，体积约 6 MB（WinForms + NativeAOT） |
| 全量扫描耗时 | < 2 秒（本机典型 20–40 项） |
| 调度触发偏差 | 相对计划时间点 < ±500 ms |
| 调度端空闲内存 | < 30 MB |

## 二、用户与使用场景

**目标用户**：Windows 上装了较多自启动软件的重度用户（开发者、设计师、装机党）。

| 场景 | 用户动作 | 期望结果 |
|---|---|---|
| **首次配置** | 打开管理端 → 看总览 → 逐条把程序加入延时启动 | 5 分钟内把 20 个自启动项排成一条合理的启动顺序 |
| **验证配置**（不重启） | 点「立即模拟调度」 | 按真实延时顺序（可加速）演示一遍，当场发现"两个程序设同一延时"这类问题 |
| **日常登录** | 无动作 | 登录后各程序按延时依次启动，调度器完成即退出 |
| **查异常** | 点失败通知 / 打开管理端 | 直接看到哪一项失败、原因是什么、连续失败几次 |
| **临时停用某项** | 列表里关掉条目开关 | 该项本次登录不启动，配置保留，原始自启动项状态不变 |
| **彻底还原** | 点「移出延时启动」 | 恢复成接管前的状态，系统按原样启动 |
| **安全体检** | 打开「系统启动项」页 | 看到服务/驱动/Winlogon 等系统级启动项（只读），服务可一键切到"延迟自动启动" |

## 三、术语表

| 术语 | 定义 |
|---|---|
| **自启动项**（Startup Entry） | 系统里已存在的、会导致某程序在登录/开机时启动的配置 |
| **软禁用**（Soft Disable） | 不删原始数据，只写"已禁用"标记让系统跳过该项 |
| **接管**（Takeover） | 软禁用原自启动项 + 把该程序纳入本软件的延时启动清单 |
| **延时条目**（Delayed Item） | 被接管、由本软件调度的条目 |
| **管理端**（Manager） | WinUI 3 主程序，负责扫描、配置、查看结果 |
| **调度端**（Scheduler） | 登录后由计划任务拉起的轻量进程，负责按延时启动各程序 |
| **模拟调度** | 在管理端按真实延时顺序（加速）跑一遍调度流程，不重启即可验证配置；可视化形式是**进度视图**（时间轴已按 D37=B 删除） |
| **稳定主键** | `source + scope + sourceKey` 三元组 + 持久化 `id`，用于可靠识别同一条目 |

## 四、产品范围

### 4.1 扫描与接管范围

| 来源 | 位置 | 可禁用 | 可延时启动 | 备注 |
|---|---|---|---|---|
| 注册表 HKCU Run | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` | ✅ | ✅ | |
| 注册表 HKLM Run | `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` | ✅ | ✅ | 需管理员权限 |
| 注册表 HKLM 32 位 | `HKLM\Software\WOW6432Node\...\Run` | ✅ | ✅ | 标记写入 `StartupApproved\Run32` |
| 用户启动文件夹 | `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup` | ✅ | ✅ | `.lnk` / `.url` |
| 系统启动文件夹 | `%PROGRAMDATA%\Microsoft\Windows\Start Menu\Programs\Startup` | ✅ | ✅ | |
| 计划任务 | 带 `LogonTrigger` / `BootTrigger` 的任务，排除 `\Microsoft\*` | ✅ | ✅ | |
| UWP / Store 应用 | `AppModel\SystemAppData\<PkgFamily>\<TaskId>` | ✅ | ⚠️ 受限 | 见 4.2 |
| 手动添加 | 任意 exe / lnk / msi | — | ✅ | 不进入"自启动项"页 |

### 4.2 UWP 的能力边界（必须写进 UI 文案）

UWP 应用的"自启动"由系统 AppModel 调度，**第三方无法延后它的启动**。可行的语义只有两条：写 `State=0` 禁止、写 `State=2` 允许。

所谓"延时启动 UWP"实际是：**禁用系统自启 + 到点由调度端 COM 激活**。这会绕过系统的启动管理，属于非常规用法，UI 必须明确说明。

> 该项对应决策点 **D4**（✅ 已批复 B：做，文案写明会绕过系统启动管理）。

### 4.3 明确不做的事（红线）

| 不做 | 原因 |
|---|---|
| 删除任何注册表值 / 移动任何用户文件 | 违反"全部可逆"原则。禁用一律走软禁用标记 |
| 接管服务、驱动 | 服务有系统原生的"延迟自动启动"机制（`delayed-auto`），另有正解；驱动启动顺序由内核 PnP 控制，人为延时会设备不可用甚至开机失败 |
| 修改 Winlogon / Userinit / Shell | 改错会导致**无法登录**。只读展示有价值（安全体检），接管没有价值 |
| 修改登录脚本 / GPO 下发的配置 | 会被组策略刷新覆盖，且破坏企业 IT 合规 |
| 启动失败后自动恢复自启动 | D17 已批复：软件不替用户改系统状态 |
| 常驻后台服务 / 开机自启管理端 | 管理端是"用完即走"的工具；常驻的只有登录瞬间的调度端，且跑完即退 |
| 批量操作（第一版） | D10 建议 B：先把单项链路跑通 |

## 五、功能性需求

### FR-1 扫描

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-1.1 | 一次扫描覆盖 4.1 表中全部来源 | 各来源的条目都出现在对应子页，计数正确 |
| FR-1.2 | 进入管理端即自动扫描一次（固定行为，不可配置） | 无需手动点刷新就能看到数据 |
| FR-1.3 | 提供手动「刷新扫描」 | 扫描期间有加载态，完成后计数与列表更新 |
| FR-1.4 | 单条读取失败不影响整次扫描 | 某个计划任务读取抛异常时跳过该项并记日志，其余条目正常显示 |
| FR-1.5 | 正确识别软禁用状态 | 键名三级回退匹配（原名 → 原名+`.exe` → 去扩展名），不得把已禁用的项误报为启用 |
| FR-1.6 | 正确识别"已被本软件接管" | 用稳定主键匹配，不因同名条目而误判 |
| FR-1.7 | 解析 `.lnk` 的真实目标与参数、提取真实程序图标 | 启动文件夹中的项显示为真实程序名与图标，而非 `.lnk` 文件名 |
| FR-1.8 | 解析 UWP 显示名 | `ms-resource://` → `SHLoadIndirectString` → MrtCache 反查 → 回退为 PackageFamilyName 前缀 |
| FR-1.9 | 标记受保护 / 只读项 | `\Microsoft\*` 下的计划任务、GPO 下发的任务显示为只读且不可操作 |
| FR-1.10 | 标记已失效项 | 目标文件不存在的条目单独标记（"已失效"），不参与延时配置 |

### FR-2 禁用 / 启用（软禁用）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-2.1 | 禁用 = 写软禁用标记，原始数据不变 | 禁用后注册表原值、文件均存在；任务管理器里该项显示为"已禁用" |
| FR-2.2 | 启用 = 删除标记值 | 恢复为系统默认状态，原值从未被改动 |
| FR-2.3 | 禁用标记写入正确的位置 | HKCU→`StartupApproved\Run`；HKLM→`StartupApproved\Run`；WOW6432Node→`StartupApproved\Run32`；启动文件夹→`StartupApproved\StartupFolder`（HKCU/HKLM 分别对应） |
| FR-2.4 | 标记数据格式正确 | 12 字节：`[0]=0x03`（禁用）/ `[1..3]=0` / `[4..11]=UTC FILETIME` |
| FR-2.5 | 写标记前确保子键存在 | 用 `CreateSubKey(path, writable: true)`，不因键不存在而失败 |
| FR-2.6 | 访问被拒时给出明确反馈 | 因 ACL / 组策略 / 只读项导致写入被拒时，指出**具体失败项与原因**，不静默失败（管理端全程提权，正常不会遇到"需要提权"场景，见 NFR-3.1） |
| FR-2.7 | 记录接管前的原始状态 | 配置中持久化 `originalState`，用于精确恢复 |

### FR-3 接管（加入延时启动）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-3.1 | 接管 = 软禁用原项 + 生成延时条目 + 持久化配置 | 三步都成功才算接管成功；任一步失败要回滚并报错 |
| FR-3.2 | 接管前记录原始状态 | `originalState.wasEnabled` 保存接管前的启用状态 |
| FR-3.3 | 自动注册调度用的计划任务 | 首次接管时创建 `DelayStartScheduler` 计划任务；已存在则更新 |
| FR-3.4 | 手动添加的条目不做任何系统改动 | 完全不动注册表/文件，UI 明确告知 |
| FR-3.5 | 支持从 exe / lnk / msi 添加 | 自动填充名称、路径；可选自定义参数 |

### FR-5 调度执行

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-5.1 | 登录后 3 秒由计划任务拉起，以最高权限运行 | 计划任务 `onlogon` + `delay 0000:03` + `RunLevel=Highest` |
| FR-5.2 | 单实例运行 | 用命名 Mutex 保证，重复触发时立即退出 |
| FR-5.3 | 时序语义 = `remaining = item.DelaySeconds - (now - 本次开始时刻)` | 是**绝对时间点**，非累加；`remaining <= 0` 时立即启动 |
| FR-5.4 | 按 `DelaySeconds` 升序、同值按 `SortOrder` 升序发起 | 输出顺序可被日志验证 |
| FR-5.5 | 逐条 try/catch，单条失败不中断后续 | 日志中有失败原因，后续条目照常启动 |
| FR-5.6 | 「普通用户」条目降权启动 | `WTSQueryUserToken` → `CreateEnvironmentBlock` → `CreateProcessAsUser`，`lpDesktop = winsta0\default` |
| FR-5.7 | 降权失败时回退直接启动并记日志 | 宁可启动成管理员，也不要启动失败 |
| FR-5.8 | 「管理员」条目继承令牌启动，不弹 UAC | 无 UAC 弹窗 |
| FR-5.9 | 启动"成功"的判定：创建成功 + 延时 1.5 秒后复查 `HasExited` | 仍存活 → 成功；已退出且退出码 ≠ 0 → 失败；已退出且退出码 = 0 → 成功（拉起已有实例的正常行为） |
| FR-5.10 | 无任何有效条目时静默退出 | 不弹窗、不显示托盘图标、不发通知 |
| FR-5.11 | 全部条目处理完后自动退出 | 不在后台常驻 |
| FR-5.12 | 写入实时状态供管理端读取 | `%LOCALAPPDATA%\DelayStart\state\current-run.json` 每次状态变化即重写（原子写） |
| FR-5.13 | 结束时归档本次结果 | `runs\<runId>.json`，保留最近 30 次 |
| FR-5.14 | 用源生成 JSON 序列化 | `JsonSerializerContext`，不用反射序列化 |

> 我原先提的"按需提权"建议**已被否，理由成立**：核心管理链路（注册调度器计划任务、HKLM 三项软禁用、系统启动文件夹、计划任务、服务 `delayed-auto`）**100% 需要管理员权限**，按需提权省不掉那次 UAC，却要额外承担提权重启、意图传递、UI 状态恢复与拒绝 UAC 时的回滚——成本高、用户零收益，还会制造"部分项处理成功、部分项失败"的半完成状态。
> 同类软件（Autoruns、`regedit`、`services.msc`、任务计划程序）均为打开即提权，用户预期已建立。完整论证见 `design-spec.md` 6.2。

## 七、数据契约

> 路径规范由 **D23** 定义，完整规则与 6 条实现约束见 `architecture.md` 1.5。核心原则：**安装目录与运行时数据完全分离，且配置文件与日志分属 Roaming / Local。**

| 文件 | 路径 | 写入方 | 读取方 | 说明 |
|---|---|---|---|---|
| 程序文件 | `%LOCALAPPDATA%\Programs\DelayStart\` | 安装器 | — | **per-user 安装、只读**；运行时数据一律不落在此（NFR-6.7） |
| 配置 | `%APPDATA%\DelayStart\config.json` | 管理端 | 管理端 + 调度端 | **Roaming**，原子写 |
| 实时状态 | `%LOCALAPPDATA%\DelayStart\state\current-run.json` | 调度端 | 管理端 | 每次状态变化重写 |
| 运行归档 | `%LOCALAPPDATA%\DelayStart\runs\<runId>.json` | 调度端 | 管理端 | 保留最近 30 次 |
| 调度日志 | `%LOCALAPPDATA%\DelayStart\logs\scheduler.log` | 调度端 | 人 | 滚动截断 |
| 管理端日志 | `%LOCALAPPDATA%\DelayStart\logs\manager.log` | 管理端 | 人 | 滚动截断 |
| 备份（弃用） | `%LOCALAPPDATA%\DelayStart\backup\` | — | — | demo 的物理备份目录，新方案主路径走软禁用，**不启用** |

字段定义见 `architecture.md` 第四节。

## 八、异常场景矩阵

必须逐条实现对应行为，且每一条都要有测试或手工验证记录。

| # | 场景 | 期望行为 |
|---|---|---|
| E1 | 某计划任务读取抛异常 | 跳过该项 + 记日志，其余照常 |
| E2 | 写 HKLM 标记被拒（ACL / 组策略限制） | 指出**具体条目**与原因，提示该项受系统策略保护，不静默失败 |
| E3 | 目标 exe 已被卸载 | 标记为"已失效"，不参与调度，列表中提示 |
| E4 | 目标 exe 启动后立即退出（退出码 0） | 判定为成功（拉起已有实例的正常行为） |
| E5 | 目标 exe 启动后立即退出（退出码 ≠ 0） | 判定为失败，记录退出码 |
| E6 | 降权启动失败 | 回退直接启动 + 记日志 |
| E7 | 调度端启动时某项延时已过期（`remaining <= 0`） | 立即启动该项 |
| E8 | 调度端被重复拉起 | Mutex 拦截，第二个进程立即退出 |
| E9 | 调度端运行中被强杀 | `current-run.json` 留下现场；管理端识别为"上次调度未正常完成" |
| E10 | `config.json` 损坏 | 保留坏文件副本、重建默认配置、提示用户 |
| E11 | 用户手动改回了注册表（重启某项自启） | 下次扫描显示"已被系统启用"，与接管状态冲突时以**用户手动改的为准**并解除接管 |
| E12 | 计划任务被外部删除 | 管理端检测到并重建，提示用户 |
| E13 | 用户连续 3 次登录某项都失败 | 保持接管不自动处理；托盘角标常驻 + 管理端常驻告警条 + 提供 `[移出延时启动]` |
| E14 | 所有延时项都被关闭（`enabled=false`） | 调度端静默退出，不发通知 |
| E15 | 系统时区/时间被修改 | 时序基于单调计时（`Stopwatch`），不受墙上时钟影响 |
| E16 | GPO 下发的计划任务 | 标记为只读，操作入口禁用 |
| E17 | 用户在 UAC 对话框选择"否" | 说明「本程序需要管理员权限才能管理自启动项」后**退出**，绝不降级运行（NFR-3.6） |
| E18 | 用户以「以其他用户身份运行」或 OTS 提权启动 | **比较提权后的用户 SID 与交互会话用户 SID**，不一致则提示不支持（NFR-3.8）。**不得用 `IsInRole(Administrator)` 代替** —— 它区分不了"正常的 UAC 自提权"与"换了个人" |
| E19 | 程序目录被移动 / 用户 profile 变更（计划任务 action 指向的路径失效） | 启动时对比 `config.json` 记录的安装路径与 `AppContext.BaseDirectory`，不一致则提示并一键 `--reinstall-task`（幂等） |
