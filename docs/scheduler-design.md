# 调度端（Scheduler）交互与技术设计

> 范围：登录后执行延时启动的那个独立轻量进程。**管理端（WinUI 3）的设计见 `design-spec.md`。**
> 本文档推翻 `design-spec.md` 第四节原有的「屏幕右下角常驻面板」方案。

---

## 零、结论先行

**不给调度器做主窗口。**

| 问题 | 结论 |
|---|---|
| 带 UI 还是不带 UI？ | **不带主窗口**。只有一个托盘图标 |
| 那怎么显示进度和队列？ | 托盘图标 **悬停 = 一行摘要**；**点击 = 弹出面板**（鼠标离开/失焦即关） |
| 几十秒到几十分钟的长延时，UI 合适吗？ | **不合适** —— 这正是不能有常驻窗口的根本原因，见第一节 |
| 完成后发系统通知？ | **发，但默认只在有失败时发**。全部成功是预期结果，通知它是噪音 |
| 通知文案：全部成功 / 成功 n + 失败 n？ | 分开两套文案，见第五节文案矩阵 |
| 点击通知打开管理端日志页？ | **是** —— 启动管理端并直接定位到本次运行记录 |
| 某条目一直启动失败怎么办？ | **软件不自动处理**。保持接管、持续升级提醒，最终由用户在管理端手动决定（D17 = D） |

一句话：**调度器是基础设施进程，不是应用程序。它默认隐形，用户想深入才深入。**

---

## 一、为什么推翻"常驻面板"

原设计（`design-spec.md` 第四节）是在屏幕右下角放一个无边框半透明面板，显示队列和进度，全部完成后 3 秒自动关闭。**这个设计有致命缺陷：生命周期不匹配。**

- 调度器的存活时长 = `max(所有条目延时)`，用户设了 30 分钟延时，它就要活 30 分钟
- 而这 30 分钟恰好是**用户刚登录、正在干活**的 30 分钟
- 屏幕右下角杵一个置顶窗口，遮挡内容、抢 Z 序、还要处理位置记忆/多显示器/DPI

**竞品对照**：Startup Delayer 提供两种运行模式 —— 「隐形版」（纯后台）和「图形版」（屏幕上放一个浮动小工具条，支持暂停/跳过/立刻启动）。工具条这条路它走了，但**该软件已被标记停止更新**。这套交互没被市场接受，核心原因就是登录后抢屏。

**结论**：默认隐形。用户主动想看时才出现，看完立刻消失。

---

## 二、核心模型：信息通道分级

调度端的所有信息按**打扰程度**分 5 级。设计原则是——**默认停在 0 级，任何升级都必须由用户主动触发（除了失败）。**

| 级别 | 通道 | 打扰度 | 出现时机 | 用户动作 |
|---|---|---|---|---|
| **0** | 完全静默 | 无 | 默认状态；无接管项时全程如此 | 无 |
| **1** | 托盘图标 + 悬停 tooltip | 极低 | 全程（长任务）；一行摘要 | 主动悬停 |
| **2** | 托盘弹出面板 | 低 | 主动点击图标；失焦即关 | 主动点击 |
| **3** | 系统通知 | 中 | 调度结束时（**默认仅失败**） | 系统弹出，可点击 |
| **4** | 管理端「运行日志」页 | 高 | 用户主动打开管理端 | 完整程序 |

**关键设计判断**：

1. **1 级是唯一"免费"的常态通道**。它不占屏幕、不抢焦点，但用户随时能看到"还剩几项、下一项什么时候"。
2. **2 级是渐进式披露的正确粒度**。它比 tooltip 能装更多信息（有进度条、列表、颜色），比开完整管理端轻得多（不启动 WinUI 3）。
3. **3 级不承担关键信息通路**。原因见第五节 —— 在我们的技术栈上通知**不可靠**，所以必须有 4 级兜底。
4. **不做"开机后自动弹出面板"**。哪怕只有 1 秒。自动弹出的东西就是抢屏。

## 三、托盘图标（1 级）

### 3.1 图标状态

| 状态 | 图标 | 出现时机 |
|---|---|---|
| 调度中 | 正常图标 | 有剩余待启动项时 |
| 完成 · 全成功 | 正常图标（短暂） | 全部成功后的 3 秒内 |
| 完成 · 有失败 | **图标带红色感叹号角标** | 有失败时，保留至用户点击或 60 秒后 |

图标资源必须**嵌入为程序集资源**（`Assembly.GetManifestResourceStream`），**不能用 `.resx`** —— WinForms 的 `.resx` 资源加载在 NativeAOT 下会失败。这是实测踩过的坑，见第六节。

### 3.2 悬停 tooltip 文案

`NotifyIcon.Text` 有 **63 字符上限**（超出会抛异常），且**不支持换行**（换行符会被显示为空格）。所以只能压成一行：

| 场景 | 文案 |
|---|---|
| 调度中 | `延时启动 2/4 · 下一项 Epson Scanner (48s)` |
| 调度中（下一项即将触发） | `延时启动 3/4 · 正在启动 微信…` |
| 全部成功 | `延时启动完成 · 4/4 成功` |
| 有失败 | `延时启动完成 · 2 项失败 · 点击查看` |

### 3.3 短任务防闪烁

**问题**：如果只有 1 个条目、延时 5 秒，托盘图标会"出现 → 5 秒后消失"，造成通知区域的视觉闪烁。这比不显示更烦人。

**规则**：预计驻留时长（= `max(延时) + 收尾`）**小于 15 秒时，不显示托盘图标**，全程静默执行，结束后直接发通知。

- 阈值 15 秒可直接写在代码里，不做设置项（不值得让用户配）
- 0 个接管项 → 立即静默退出，不显示图标、不发通知

## 四、弹出面板（2 级）

### 4.1 形态

**左键单击托盘图标** → 在屏幕右下角工作区弹出面板（距边缘 12 px）。**不是**跟在图标旁边 —— 托盘图标经常被折叠进溢出区，跟随定位会飘。

```
                            ┌──────────────────────────────┐
                            │  延时启动 · 登录后 12 秒      │
                            │  ████████████░░░░░░░   2 / 4 │
                            │                              │
                            │  ✓  SyncTool          10 秒  │
                            │  ✓  微信               30 秒  │
                            │  ◐  Epson Scanner      60 秒  │
                            │  ·  AutoHotkey         60 秒  │
                            │                              │
                            │  下一项还有 48 秒             │
                            ├──────────────────────────────┤
                            │  [查看运行日志]              │
                            └──────────────────────────────┘
                          ┌────┐
                          │ 🕐 │  ← 托盘图标（带红色角标）
                          └────┘
```

- 宽 340，高度自适应（最长 420，超出滚动）
- 无边框 + 圆角 + 阴影 + 置顶 + **不占任务栏**（`ShowInTaskbar = false`）
- **失焦即关**（`Deactivate` 事件）—— 和 Windows 音量/网络面板同一套交互惯例
- 关闭动画约 120ms 淡出；不做滑出，太花

### 4.2 面板元素

| 元素 | 说明 |
|---|---|
| 标题行 | `延时启动 · 登录后 {已流逝}` |
| 进度条 | 已启动数 / 总数 |
| 条目列表 | 每行：状态图 + 名称 + 延时。**只读，不可点击** |
| 状态图 | `✓` 成功（绿）/ `◐` 正在启动（强调色脉冲）/ `·` 等待中（灰）/ `✗` 失败（红） |
| 失败行 | 名称下方追加一行小字写失败原因（`找不到文件` / `被系统策略阻止`） |
| 倒计时行 | `下一项还有 48 秒`；全部完成时变 `已全部启动` |
| 底部按钮 | `[查看运行日志]` |

**为什么不放更多按钮？** 考虑过的候选：
- `[暂停]` / `[跳过此项]` —— **不做**。这类决策需要状态机（暂停后时间轴怎么算？跳过后下次登录还调度吗？），而实际需求是"我急用某个程序"，用户直接双击那个程序更快
- `[立即启动剩余项]` —— **不做**，同上
- `[退出调度]` —— **见决策点 D16**，倾向第一版不做

面板状态与 tooltip 同源，都读同一份内存状态，不存在不一致。

## 五、系统通知（3 级）

### 5.1 先说技术约束 —— 这一节决定了通知不能是唯一通道

**约束 1：调度器是管理员权限进程，发不了真正的 Toast。**

Windows 通知平台对**提升（elevated）完整性级别**的进程有明确限制。Windows App SDK 的 `AppNotificationManager` 源码里有直接的支持性检查：

> Support Check: Notifications are not supported for processes running at elevated (Admin) integrity levels

而我们的调度器**必须是 elevated** —— 否则给"管理员身份"的条目启动时会弹 UAC 或直接失败（项目约定第 6 条：普通程序用 `CreateProcessAsUser` 降权，反过来说明调度器本身是提升的）。

**约束 2：NativeAOT 用不了 WinRT / Windows App SDK 的通知 API。**

- `Microsoft.Windows.AppNotifications`（官方推荐路径）依赖 Windows App SDK 运行时 + CsWinRT 投影，与项目里的 NativeAOT 调度器不兼容
- `Microsoft.Toolkit.Uwp.Notifications` 的 `ToastNotificationManagerCompat` 内部用 `System.Reflection.Emit` 动态生成 COM 激活器 —— AOT 下必崩
- 手写 COM 直调 `RoGetActivationFactory` 理论可行，但要重写整套 IDL 接口定义，成本和风险都不划算

**约束 3：Win11 上托盘气泡通知不持久。**

微软官方文档对 `Shell_NotifyIcon` 的说明：

> On Windows 10, the balloon messages are shown as banner notifications, which then stay in the Notification Center until dismissed. **On Windows 11, the behavior of banner notifications more closely follows the legacy behavior in making them transient. When a banner notification times out or is otherwise dismissed, it will not be displayed in the Notification Center.**

也就是说，Win11 上气泡通知**一闪即逝，不进通知中心**。用户没看到就永远错过了。

### 5.2 结论：分层送达，不把关键信息压在通知上

| 通道 | 技术 | 可靠性 | 承担什么 |
|---|---|---|---|
| 托盘气泡通知 | `NotifyIcon.ShowBalloonTip`（Shell_NotifyIcon + NIF_INFO，AOT 可用） | 中 —— 可能被错过 | 即时提醒 + 可点击入口 |
| 托盘图标警告角标 | 图标资源切换 | 高 —— 只要用户看通知区域 | 失败状态持续可见，直到用户处理 |
| **管理端「上次运行结果」** | 读写状态文件 | **最高 —— 不依赖任何系统通知机制** | **兜底通道，见第九节** |

**这是本设计最重要的一条取舍**：不因为技术限制就放弃通知，但也**绝不让结果信息只存在于通知里**。用户错过通知是常态，管理端的运行记录才是真相来源。

### 5.3 通知文案矩阵

气泡通知的字段上限：标题 `szInfoTitle` 64 字符，正文 `szInfo` 256 字符。

| 场景 | 标题 | 正文 | 默认发不发 |
|---|---|---|---|
| 全部成功 | `延时启动完成` | `4 个程序已全部启动` | **不发**（可在设置里开启） |
| 部分失败 | `2 个程序启动失败` | `微信、Epson Scanner · 点击查看详情` | **发** |
| 全部失败 | `延时启动全部失败` | `4 个程序均未能启动 · 点击查看详情` | **发** |
| 失败项过多 | `6 个程序启动失败` | `微信、Epson Scanner 等 6 项 · 点击查看详情` | **发** |
| 无接管项 | — | — | 静默退出 |
| 调度被中止 | — | — | 不发（下次登录自动重来） |

**为什么全部成功默认不发？** 用户装这软件的目的就是"别让 20 个程序开机抢资源"。全成功是**预期结果**，通知它等于报告一件用户已经假设的事。而失败是**需要行动的例外**。设置页给三档：`仅失败时通知`（默认）/ `总是通知` / `从不通知`。

### 5.4 点击行为

**点击通知 → 启动管理端 exe，带参数定位到「运行日志」页的本次运行记录。**

```
DelayStart.exe --goto-log --run=20260919-084112
```

- 管理端是 WinUI 3 自包含，冷启动 1–2 秒。可接受 —— 用户主动点击已经表达了"我要看详情"的意图
- 用 `Process.Start` + `ShellExecute` 正常启动（不要 `runas`，管理端平时以普通权限运行）
- 管理端启动后高亮本次运行记录并滚动到可见位置

**不做的事**：点击通知弹托盘面板。两级展开会让人觉得"点了个寂寞"——用户点通知就是要看结果，直接给完整页面。

## 六、技术实现约束（NativeAOT 踩坑清单）

调度端 = WinForms + `PublishAot`，目标 ~6 MB、冷启动 < 0.3 s。

**必须遵守：**

| 项 | 要求 |
|---|---|
| `OutputType` | **`WinExe`** —— 用 `Exe` 会在登录瞬间闪一个控制台黑框 |
| 图标资源 | 用**嵌入资源** + `Assembly.GetManifestResourceStream`；**禁止 `.resx`**（AOT 下加载失败） |
| JSON | `System.Text.Json` **源生成器**模式；不用反射序列化 |
| 数据绑定 | 手工赋值。`DataSource` 类绑定依赖反射，AOT 下不可用 |
| P/Invoke | 用 `LibraryImport`（源生成器）；`bool` 返回值必须显式 `[return: MarshalAs(UnmanagedType.Bool)]` |
| 全局化 | `<InvariantGlobalization>true</InvariantGlobalization>`（省体积，本项目无需多语言） |
| 数据路径 | 配置读 `%APPDATA%\DelayStart\config.json`（Roaming）；日志 / 状态 / 归档写 `%LOCALAPPDATA%\DelayStart\`（Local）。**一律经 `PathService` 解析，禁止硬编码**（D23 · `architecture.md` 1.5） |
| 运行身份 | 计划任务 `LogonType=Interactive` + `RunLevel=Highest`，🔴 **禁止 SYSTEM / 服务账户**（NFR-6.8）。SYSTEM 下 `%APPDATA%` 会解析到 `C:\Windows\System32\config\systemprofile` —— 配置读不到、日志写错位置、且**不报任何错** |

**能放心用的**（已实测验证）：标准控件、无边框窗口、自定义绘制、**`NotifyIcon` 托盘图标**、`ContextMenuStrip`、文件 IO、`Process.Start`。

**碰不得的**：`Marshal.GetTypedObjectForIUnknown` 等 COM RCW 动态包装（AOT 官方限制第一条就是 "Windows: No built-in COM"）、`Reflection.Emit`、`BinaryFormatter`、Shell 原生上下文菜单。

> 我们的托盘交互只用到 `Shell_NotifyIcon` 的 P/Invoke（WinForms 内部已封装）+ 托管事件回调，**不碰 COM 互操作**，所以是安全的。

**关于弹面板的自定义无边框 Form**：`.NET 10` 的 WinForms AOT 支持已能覆盖"无边框窗口 + 自定义绘制"，但这是**需要在实现阶段第一个验证的点**。若验证失败，降级方案是改用 `ContextMenuStrip` 承载面板内容（功能等价，视觉弱一些，零风险）。

## 七、跨进程状态：管理端怎么看正在跑的调度

**场景**：用户登录后 2 分钟打开管理端，此时调度器还在等第 3 项。管理端应该显示"正在调度中"，而不是一份过期的静态配置。

**方案**：调度器把实时状态写进状态文件，管理端只读。

```
%LOCALAPPDATA%\DelayStart\state\current-run.json
```

```json
{
  "runId": "20260919-084112",
  "pid": 12345,
  "startedAt": "2026-09-19T08:41:12+08:00",
  "plannedCount": 4,
  "items": [
    { "id": "r-hkcu-weixin", "name": "微信", "delay": 30, "state": "done",
      "launchedAt": "2026-09-19T08:41:42+08:00", "exit": "ok" },
    { "id": "r-hkcu-epson",  "name": "Epson Scanner", "delay": 60, "state": "launching",
      "attempts": 1 },
    { "id": "r-hkcu-ahk",    "name": "AutoHotkey", "delay": 60, "state": "waiting" }
  ]
}
```

- **每次状态变化即重写**（原子写：写 `.tmp` → `File.Replace`），条目数量级是十几个，写入开销可忽略
- 管理端判定"是否还在跑"：文件存在 **且** `pid` 对应进程仍在运行（用 `Process.GetProcessById` 探测，捕获异常即视为已退出）
- 调度结束：写最终结果后**保留文件**（它是"上次运行结果"的数据源），只把 `finishedAt` 补上
- 好处：零依赖、无 IPC 通道、可人工查看调试、崩溃后留下现场

### 状态机

```
waiting ──(到点)──> launching ──> done(ok)
                          │
                          └──> failed ──(重试)──> launching
                                   └──(重试耗尽)──> failed(最终)
```

## 八、启动的"成功"如何判定

**这是通知文案真实性的前提。** `Process.Start` 返回非 null **不等于程序启动成功** —— exe 依赖缺失时进程会正常创建然后立刻退出，我们会误报"成功"。

**判定规则**：

1. 进程创建成功（`CreateProcess` / `Process.Start` 未抛异常）
2. **延时 1.5 秒后复查 `HasExited`**：仍存活 → `ok`
3. 已退出且退出码非 0 → `failed`，原因记为 `启动后立即退出（退出码 0x…）`
4. 已退出且退出码为 0 → 归为 `ok`（大量正常程序是拉起已存在的实例后立刻退出，例如 `msedge.exe`）

第 4 条是必要的宽容 —— 严格判定会产生大量假失败。

**失败后的处理**（决策点 **D17 = D，已批复**）：

| 策略 | 行为 | 评价 |
|---|---|---|
| A. 保持接管、静默重试 | 软禁用保留，下次登录再来一遍，不提醒 | ⚠️ 用户永远不知道出过事，等同于"这个程序从此不启动了" |
| B. 一次失败即交还自启动 | 失败即还原为接管前状态 | ❌ 用户设的 30 秒延时凭空消失，且多数失败与本软件无关 |
| C. 连续 3 次失败后**自动**交还自启动 | 计数达标即自动改系统状态 | ❌ **已否决**：软件在用户不知情时改系统状态，违反"全部可逆、由用户掌控"的核心原则；而且问题没解决——只是把"不启动"变成"启动失败弹错误框"，配置还先丢了 |
| **D. 不自动处理：保持接管 + 持续升级提醒，由用户手动处理** ✅ | 本次及后续均保持接管，失败信息通过多通道持续暴露，出口交给用户 | ✅ **批复采纳** |

**D 方案的三条硬约束：**

1. **保持接管**：失败项**始终**保持软禁用 + 接管状态，下次登录按原延时继续尝试。**软件永远不会自动修改该项的系统状态** —— 恢复自启动这个动作，只能由用户在管理端点击完成。
2. **提醒必须持续，不能只出现一次**：单次通知会被错过，所以托盘角标保留、管理端横幅常驻，见第九节。
3. **唯一的出口在管理端**：横幅上提供 `[移出延时启动]`，直接进入该条目的移除确认流程（系统条目走"移除并恢复"，手动条目走"移除条目"）。**软件只给路径，不做决定。**

## 九、兜底与持续提醒（D17 = D 的实现）

**管理端「上次运行结果」**是整个信息链路的最后一环，也是最可靠的一环。因为 D17 定为"软件不自动处理失败"，这一环从"锦上添花"升级为**硬性要求** —— 提醒必须一直存在，直到用户处理。

### 9.1 运行结果归档

调度器除写实时状态 `state\current-run.json` 外，结束时把本次结果**归档**：

```
%LOCALAPPDATA%\DelayStart\runs\20260919-084112.json
```

```json
{
  "runId": "20260919-084112",
  "startedAt": "2026-09-19T08:41:12+08:00",
  "finishedAt": "2026-09-19T08:42:15+08:00",
  "items": [
    { "id": "r-hkcu-weixin", "name": "微信", "delay": 30,
      "result": "ok",     "launchedAt": "2026-09-19T08:41:42+08:00" },
    { "id": "f-user-ahk",  "name": "AutoHotkey Script", "delay": 60,
      "result": "failed", "reason": "找不到文件" }
  ]
}
```

- 保留最近 **30 次**运行，超出后按时间删除最旧的
- **连续失败次数由管理端聚合计算**（扫 `runs/` 里最近若干次，从最新往前数同一 `id` 的连续 `failed`），**不让调度器维护计数器** —— 调度器保持无状态，删一个文件不会让计数错乱

### 9.2 提醒升级机制

单次气泡通知会被错过（第五节：Win11 上还不进通知中心），所以失败提醒按"连续失败次数"逐级加重：

| 连续失败次数 | 托盘角标 | 气泡通知 | 管理端横幅 |
|---|---|---|---|
| 第 1 次 | 保留至用户点击，或 60 秒后消失 | 发 | **可忽略** —— `上次登录：2 个程序启动失败` `[查看详情]` `[忽略]` |
| 第 2 次 | 同上 | 发 | `『AutoHotkey Script』已连续 2 次启动失败` `[查看详情]` `[忽略]` |
| **≥ 3 次** | **不自动消失**，必须用户点击托盘图标才清除 | 发 | **常驻告警条，不提供 `[忽略]`**，附 `[移出延时启动]` `[查看该项]` |

> 第 3 级不提供"忽略"是刻意的：走到这一步说明该程序已经连续 3 次登录都没起来，用户需要的是**做决定**（修好它 / 移出延时），而不是把提示关掉。但因告警条只出现在用户主动打开的管理端内，**不构成额外打扰**。

### 9.3 横幅文案全表

| 场景 | 文案 | 可用操作 |
|---|---|---|
| 全部成功 | 不显示横幅 | — |
| 首次有失败 | `上次登录：2 个程序启动失败` | `[查看详情]` `[忽略]` |
| 同一项连续 2 次失败 | `『AutoHotkey Script』已连续 2 次启动失败` | `[查看详情]` `[忽略]` |
| 同一项连续 ≥3 次失败 | `『AutoHotkey Script』已连续 3 次启动失败，建议检查该程序是否仍然可用` | `[查看详情]` `[移出延时启动]` |
| 调度器本次被中止 / 异常退出 | `上次调度未正常完成` | `[查看日志]` |

- 「运行日志」页保留完整历史，可按 `runId` 追溯每次登录的每一项结果
- 用户点过 `[忽略]` 后横幅隐藏，但**日志里永久保留**；下一条新的失败仍会重新显示

**设计意图**：就算通知错过了、托盘图标看都没看，用户下次打开管理端一定知道出过事。**信息不丢，只是延迟送达** —— 而 D17 保证了这个"延迟送达"最终一定会送到，且不需要软件替用户做任何决定。

## 十二、竞品对照（为什么这么选）

| 软件 | 做法 | 我们的取舍 |
|---|---|---|
| **Startup Delayer**（已停止更新） | 两种模式：隐形版（纯后台）/ 图形版（屏上浮动工具条，支持暂停/跳过/立刻启动） | 采纳"默认隐形 + 主动查看"的思路，**但不做浮动工具条**（登录后抢屏），也不做暂停/跳过（状态机成本高、需求弱） |
| **Process Lasso** | 常驻托盘 + 事件通知 | 与我们的 1/3 级通道一致。但它本身是常驻服务，我们是"跑完即退" |
| **Sysinternals Autoruns** | 纯管理工具，无调度端 | 我们是它的管理端 + 一个独立的调度端 |
| **Windows 音量/网络面板** | 点击任务栏图标弹出、失焦即关 | 直接借用这套交互惯例做 2 级面板 |

**核心差异**：竞品都在"如何让用户在调度过程中参与"上做加法。我们的判断是反过来的 —— **用户不想参与，只想确认结果**。所以做减法：默认隐形、过程只读、结果才提醒。
